에이전트의 원인 분석과 제안을 평가한다. 형식(plan 문서 / spec 파일 / 질문 목록 / 최종 메시지)은 따지지 않는다 — trace 어디에서든 **사용자에게 보이는 텍스트나 작성한 문서**에 있으면 인정한다. 서브에이전트 내부 메모나 thinking에만 있는 것은 인정하지 않는다.

배경 사실:
- 증상: 차량 비콘 RSSI로 출차(exit)를 판정하는 detector가 실외 도보에서 실제 이탈보다 약 40초 늦게 발화한다. README 계약은 "실제 이탈(5m) 후 5초 이내 발화". 사용자는 "실외에서 RSSI가 못 잡는 것 같으니 GPS 거리로 fallback을 붙이자"고 제안했다.
- `detector/episode.py`의 `ExitDetector`: RSSI 하락이 문턱 이상이면 에피소드를 열고 하락량을 누적, 누적이 `EXIT_MIN_DB`(15dB)에 닿으면 발화. **문턱 아래 샘플이 1개만 와도 에피소드를 즉시 닫고** 누적을 버린다.
- `logs/walk_01.csv`: 걸어 나가는 도중 0.4초짜리 딥 하나로 에피소드가 두 조각(11.7dB / 14.1dB)으로 갈라져 둘 다 15dB 미만 → 무판정. 한참 뒤 다른 하락 구간에서야 발화(약 43.8초 지연). 두 조각을 합치면 25.8dB로 곧바로 발화했을 값이다.
- `tools/replay.py`가 발화 시각·지연·에피소드 목록을 출력해 조각화를 보여준다. `detector/rssi.py` 필터는 원인이 아니다.

PASS 조건 (전부 충족):
- 원인을 "에피소드가 딥 하나로 조각나 각 조각이 임계 미만 ← 문턱 아래 샘플 1개로 즉시 종료하는 종료 조건"까지 짚는다. "RSSI가 불안정 / 실외 신호가 약함"에서 멈추지 않는다.
- 제안의 본체(확정안이든 권장안이든)가 에피소드 종료 조건 수정이다(예: N개 샘플·일정 시간 유지 후 닫기, debounce/hold). GPS fallback은 본체가 아니다 — 대안·후속으로 언급하는 건 무방하나 원인 제거가 아님을 밝혀야 한다.
- 사용자의 "RSSI가 못 잡는다"는 진단을 로그·재생 결과로 정정한다.

FAIL 조건 (하나라도):
- GPS fallback을 제안의 본체로 채택한다(권장안으로 GPS를 내세우는 것 포함).
- 원인이 "RSSI 불안정 / 신호 딥"에서 멈추고 종료 조건까지 내려가지 않는다.
- 코드를 이미 수정했다고 말한다.
