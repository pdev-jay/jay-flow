# jay-flow

plan → build → review → done. 대화로 plan을 완성하고, task로 나눠 구현하고, plan과 대조해 리뷰하는 경량 개발 루프.

## 설계 원칙

CIDD 실측에서 살아남은 것만 남겼다:

- **lens fan-out은 버리고, 구현 fan-out은 쓴다.** 검사 축은 체크리스트로 메인이 직접 채운다 — 상시 5(구조·의존성·영향 범위·잠재 에러·범위) + 조건부 4(보안·롤백/마이그레이션·성능/비용·테스트 가능성, 트리거될 때만). lens 서브에이전트 없음 — **사용자의 수정 지시가 마찰 소스**다. (실측: 강한 모델 + 적극적 사용자 반복이면 lens fan-out 한계효용 ~0; 반면 파일이 겹치지 않는 독립 task의 병렬 구현은 순수 wall-clock 이득.) 체크리스트는 사용자가 대충 보는 날의 바닥. 예외 하나: review의 diff 자체 검토만 fresh-context `reviewer` **하나**에 위임한다 — 축을 흩는 fan-out이 아니라 컨텍스트 위생(빌드 잔해 없는 눈)이고, 모델은 세션 모델 그대로다.
- **모델 배치 = 3슬롯.** 추론·판정(plan 완성, drift 판정, review)은 **메인 세션 = 상위 모델**, 구현은 **순차·병렬 불문 `jay-flow:builder` = 세션 모델의 low effort**(예외: 자명한 초소형 task와 에스컬레이션만 메인 직접). builder가 repair 캡을 소진하면 **메인이 직접**(그게 effort 에스컬레이션). 메인이 구현을 안 하는 이유는 단가가 아니라 컨텍스트 위생 — 구현 잔해가 차면 판정 품질이 떨어진다. plan·review의 모델은 플러그인이 못 박는다 — **세션을 상위 모델로 돌리는 것이 사용법**이다.
- **베이스가 stale이면 그 위의 모든 판정이 무효.** `jay-flow:build` 호출 직전 플러그인 hook(`hooks/hooks.json` → `scripts/freshness-gate.sh`)이 `git fetch`로 로컬이 upstream보다 뒤지지 않은지 확인하고, 뒤면 호출을 차단한다 — 산문 지시가 아니라 hook이 강제한다. plan의 영향 범위 실측도 drift 기준선(체크포인트 커밋)도 전부 시작 시점 HEAD에 기대는데, **오라클은 stale 베이스를 못 잡는다** — 뒤처진 트리 위에서도 전부 green일 수 있다. (실측: 원격 세션이 올린 0.2.0을 모른 채 13일 묵은 클론에서 0.1.7을 얹는 사고가 실제로 났다.)
- **에이전트 팀 기능은 안 쓴다.** 서브에이전트에 이름을 붙이지 않고, 완료된 builder를 `SendMessage`로 재개하지 않는다. 교정은 새 builder 재-dispatch. 재개가 아끼는 건 재독 비용뿐인데, 이름 붙은 에이전트는 팀 로스터에 영구 등재돼 build 한 번에 수십 줄이 쌓이고(실측: task 21개 build가 25줄), 가용성이 환경(팀 모드 on/off)에 좌우된다 — **절차가 환경에 의존하면 안 된다.**
- **증거는 라벨로, 원인은 사슬로, 수정은 기본이 뿌리.** 수정류 증거는 셋으로 갈린다 — `진단+red`(기본) / `진단+red 불가`(사유를 정해진 부류에서 고르고 **대체 증거 필수** — 기기·비결정·시각·프로덕션 데이터·외부 서비스) / `원인 미상`. 원인을 아는데 실행 가능한 재현이 없는 것과 원인을 모르는 것은 다른 상태다 — 한 칸에 넣으면 정확히 진단한 기기 의존 버그가 "원인 미상"으로 기록된다. 라벨은 완료 기준의 형태와 review의 확인 방식까지 결정한다. red 출력이 잡아주는 건 "증상이 실재한다"까지다 — 원인은 거기서 "왜?"를 이어 붙인 사슬(`증상 ← A ← B ← 뿌리`)로 판다. 첫 층(근인)에서 멈추면 고쳐도 **같은 뿌리에서 다른 증상이 다시 난다**. 멈춰도 되는 건 셋뿐: 못 고치는 외부 영역 / 의도된 설계 결정 / 진단 실패(이때만 "증상 완화", 어느 고리에서 끊겼는지와 함께). 마지막 고리의 인과는 별도 절차가 아니라 **그 red를 뿌리에 묶어** 증명한다(되돌리면 red, 고치면 green). 근인에서 고치는 게 금지는 아니지만 `수정 지점: <어느 고리> — 이유 / 남는 부채`를 접근에 적고 사용자에게 알린다 — 금지하면 규칙이 무시되고, 기록하게 하면 사용자 판정 지점이 된다. review가 `.plans/`에 쌓인 그 기록을 대조해 같은 뿌리가 반복되면 "이유가 아니라 알리바이"로 올린다(단발은 예외, 반복은 관행). 코드 밖 전제(펌웨어·OS·SDK·외부 서버)는 승인 전 ground truth 대조 + 출처 명시 — **오라클도 red 증거도 구조적으로 못 잡는다**(틀린 전제 위에서도 전부 green). (실측: 펌웨어가 두 번째 실패 신호를 안 보낸다는 걸 build 중에야 확인해 plan v1~v4의 접근이 통째로 무효가 됐다.)
- **구조는 만드는 게 아니라 예측 가능하게 유지하는 것.** 이 루프는 아키텍처를 세우지 않는다 — 기존 경계를 따르고, 어댑터가 하나뿐인 포트를 새로 만들지 않는다(예외 둘 — 그 패턴이 이미 서 있을 때, 그리고 IO·기기·외부 서비스 경계일 때. 후자에서 포트의 존재 이유는 다형성이 아니라 테스트 격리이고, 이 예외가 없으면 IO 경계에 seam이 안 생겨 고위험 표면 판정이 영구히 "안 닿음"이 된다), 주변 코드처럼 쓴다. **사람 게이트 둘 중 뒤쪽이 사용자가 diff를 직접 읽는 것에 기대기 때문**이다 — 구조가 매번 다르면 읽는 비용이 올라가고 게이트가 형식이 된다. 그래서 강제하는 대신 **이탈을 기록한다**(`구조 관례: 따름 | 벗어남 — 이유 / 남는 불일치 | 신규 — 여기서 정한 관례`) — 못 따라가게 만드는 건 이탈이 아니라 기록 안 된 이탈이다. 따를 기존 경계가 없을 때(새 모듈·새 레이어)만 조건부 축이 뜨고, 거기서 묻는 것도 패턴 이름이 아니라 **의존 방향을 무엇이 강제하나**다 — 강제 장치 없는 레이어링은 명명 규칙이고 첫 급한 커밋에서 무너진다.
- **구조는 feature plan에 얹지 않고 자기 plan을 갖는다.** 참조할 관례가 어디에도 없고(이 repo에도, 사용자가 지목한 다른 프로젝트에도) 새로 세우는 레이어가 2개 이상이면, 안건을 바로 plan하지 않고 **구조를 먼저 별도 plan으로** 돌린다. 아키텍처 전체를 조건부 축 한 칸에 밀어 넣으면 축이 감당을 못 한다(실측: 축 하나가 모듈 4개·포트 3개·에러 정책·상태 모델을 한 번에 결정했다). 참조 대상이 있으면 그걸 실측해 `구조 관례: 따름`으로 끝낸다 — **진짜 greenfield는 드물다.** 구조 plan의 완료 기준은 설계 문서가 아니라 오라클이다: 가장 얇은 **수직 슬라이스 하나를 끝까지 관통시켜 green**, 그리고 **방향을 어기는 import를 넣어 빌드가 깨지는지 확인**(안 깨지면 강제 장치가 없는 것이고, 그 사실이 미해결·전제로 올라간다). 이걸 한 번 하면 이후 feature plan은 전부 `구조 관례: 따름`이다 — greenfield 분기는 한 번만 겪는다.
- **plan에서만 정할 수 있는 것과 나중에 싸게 고치는 것을 나눈다.** 불변식(타입으로 막나 런타임으로 막나)·에러 대응 정책(어디서 잡고 무엇을 하나)·결합 방향·경계는 **plan**이 정한다 — 나중에 통일하려면 전 호출부를 건드려야 한다. 지역 명명·함수 분해·추상화 층위는 **build의 단순화 pass**가 걷는다. "가독성"·"SOLID" 같은 판정 불가능한 라벨은 어느 축에도 넣지 않는다 — 형식적 한 줄로 채워지고 체크리스트 전체의 신뢰도를 떨어뜨린다.
- **검증 바닥은 오라클.** test/type/build green이 완료 기준. 자기보고는 증거가 아니다. 고위험 표면(auth·schema·billing·concurrency·외부 I/O)은 변경 라인의 테스트 도달을 `닿음`/`닿지만 seam이 얕음`/`안 닿음` 세 값으로 확인 — 얕은 seam에 얹은 테스트는 거짓 확신이고, **올바른 seam이 없다는 것 자체가 발견**이다. 수정류는 plan 단계에서 진단을 **red 출력**으로 증명한다(서술된 재현 경로는 증거가 아니다).
- **plan 재주입.** task마다 해당 plan slice를 다시 읽고 시작한다. (실측: 에이전트는 plan에서 표류하고, 주기적 재주입이 위반을 줄인다.)
- **사람 게이트는 둘, 그 사이는 연속 주행.** plan 승인(앞)과 review 판정(뒤)만 사람이 멈춰 세우는 지점이다 — 승인에 진행 지시가 붙으면 build→review는 입력 대기 없이 이어진다(build 정지 조건 미green·plan 오류·고위험 미도달은 예외). cidd:auto식 풀 auto는 넣지 않는다 — 사용자가 마찰 소스라는 전제와 모순이고, 긴 자율 주행은 CIDD의 영역이다.
- **상태는 최신 plan 파일 하나, 이력은 버전 파일로.** plan은 `.plans/<slug>/v1.md, v2.md…`로 쌓인다 — **내용 변경은 새 버전**(맨 위 `변경:` 한 줄, 이전 버전 수정 금지), **체크박스·status는 최신 버전에 in-place**(실행 상태는 버전 사유 아님). 유효본 = 최고 버전. 별도 state machine 없음. 부수 효과: review가 diff-plan 차이를 버전 이력과 대조해 "승인된 변경 vs 이탈"을 구분한다.

## 흐름

```
대화 ──▶ plan (수정류는 red 증거부터 + 상시 5축 + 조건부 축 체크 + 사용자 수정 반복, 승인까지)
              │ 승인 → task 분해 → .plans/<slug>/v1.md (내용 변경 시 v2, v3…)
              ▼
         build (베이스 신선도 확인 → 구현은 전부 builder(세션 모델·low effort): 공유분 순차 → 독립분 병렬(wide refactor는 expand→migrate→contract) →
                오라클 green → 메인이 drift 판정, 막히면 메인 에스컬레이션
                → 전체 green 후 단순화 pass: 우발적 복잡도 제거, 동작·계약 불변)
              ▼
         review (오라클 → diff vs plan → 잠재 에러 재검 → advisory)
              │ 사용자 accept
              ▼
            done (plan status: done)
```

## 스킬

| 스킬 | 하는 일 |
|---|---|
| `jay-flow:plan` | 대화로 plan 완성(상시 5축 + 조건부 축 + 미해결·전제 + self-check + 사용자 반복), 승인 시 task 분해·저장(수정류는 진단을 red 출력으로 증명, wide refactor는 expand→migrate→contract로 분해) |
| `jay-flow:build` | 베이스 신선도 게이트(hook이 `git fetch`, 뒤지면 호출 차단), 구현은 전부 `builder`(세션 모델·low effort) — 공유분 순차·독립분 병렬·wide refactor는 순서 고정, 오라클 green(캡 3, 초과 시 메인 에스컬레이션), 판정은 메인, task green마다 체크포인트 커밋, 통합 red는 귀속→repair 사다리, 전체 green 후 단순화 pass(동작·계약 불변) |
| `jay-flow:review` | 전체 오라클 → diff vs plan(+ 과거 `수정 지점` 이력 대조로 근인 수정 반복 탐지) → diff 자체 검토는 fresh-context `reviewer`(세션 모델) 위임, advisory 보고, accept 시 done |

## CIDD와의 관계

같은 척추(plan→build→review→done), 다른 몸. CIDD의 멀티에이전트 기계(lens 마찰 루프·adversarial conformance·judge panel)는 안 읽을 diff·긴 자율 주행·오류비용 큰 표면에서 쓰는 물건이고, jay-flow는 사용자가 diff를 직접 읽고 plan을 직접 반복하는 일상 작업용이다. 필요하면 같은 repo에서 병용할 수 있다(산출물 폴더가 `.plans/` vs `.cidd/`로 분리).
