# jay-flow: plan

핵심 원리: **사용자가 마찰 소스다.** lens 서브에이전트 fan-out 없음 — 검사 축은 체크리스트로 메인이 직접 채우고, 반복은 사용자의 수정 지시로 돈다. plan 오류는 전 task로 전파되고 오라클이 못 잡으므로(틀린 설계도 컴파일은 된다), 여기가 이 루프에서 가장 공들일 단계다.

## 절차

시작할 때 `.plans/`에 task 체크박스가 전부 `[x]`인데 status가 `in-progress`인 plan이 있으면 한 줄로 알린다 — review·accept에 닿지 않아 done 처리와 그에 붙은 절차(구조 plan의 문서 반영 등)가 빠진 상태일 수 있다. 알리기만 하고 대신 닫지 않는다.

1. **목표·원인 확정 (대화).** 무엇을(목표)과 **왜(원인·배경)**를 분리해 적는다. 안건이 모호하면 되묻는다 — 단, repo에서 알 수 있는 것(구조·기존 패턴·유사 구현)은 묻지 말고 Read/Grep으로 직접 확인한다. 사용자 머릿속에만 있는 것(왜 하는지, 안 되는 방향, 암묵 제약)만 묻는다.
   - **목표는 관측 가능한 수용 기준(AC)과 비목표로 적는다.** AC = 끝났을 때 밖에서 확인할 수 있는 동작 하나씩(`AC-1: <조건> → <관측 결과>`). 비목표 = 사용자가 명시적으로 뺀 것. 사용자가 말하지 않은 비목표를 지어내거나 AC를 약하게 고쳐 쓰지 않는다 — 범위를 몰래 줄이는 통로가 된다. AC는 5단계에서 task의 완료 기준으로 하나도 빠짐없이 매핑된다.
   - **사용자가 제시한 해법은 의도의 증거지 원인의 증거가 아니다.** 사실(관측된 것)·기술 가설·사용자 결정을 섞지 않고 구분해 적는다.
   - **모델·effort 추천 (근거가 있을 때만, 한 번).** 세션 모델 그대로 시작한다. 조사로 **구체 근거**가 생겼을 때만 목표 설정 하나와 이유 하나를 한 줄로 낸다 — `권장: Opus high — 생명주기 순서 + 원인 후보 둘`. 기준은 경로·파일 수·소요 시간이 아니라 작업 성격이다: 결정적·대량 반복은 낮은 모델/effort, 일반 엔지니어링은 중간, 원인 후보 여럿·동시성·생명주기·아키텍처 트레이드오프는 high, 서로 다른 수정 시도가 반복 실패하면 한 단계 위. 조언이지 제어가 아니다 — 모델을 바꾸지 않고, 진행을 막지 않고, 대안을 늘어놓지 않고, 같은 근거로 반복하지 않는다(새 강한 근거가 생길 때만 한 단계 위로 다시). 바꿀지는 사용자가 정한다.
   - **분석·진단·요구 정리만 요청받았으면 거기서 멈춘다.** 그 요청은 코드 수정도 `.plans/` 저장도 승인하지 않는다 — 결과(문제 정의·진단·plan 초안)를 대화로 돌려준다.
   - 수정(fix)류 — 증거에 라벨을 붙인다. 셋이고 기본은 첫째다. 서술된 재현 경로는 어느 라벨의 증거도 아니다. 증거 없이 세운 진단은 오진이 전 task로 전파되고, 틀린 원인을 고쳐도 컴파일은 되므로 오라클이 못 잡는다.
     - `진단 + red` (기본). 증거는 red 출력이다: 명령 하나를 이름 대고(테스트 호출·스크립트 경로·curl), 이미 한 번 돌려서 그 호출과 출력을 보여라. 조건 둘. ① 사용자가 말한 그 증상에 assert할 것 — "에러 안 남"이나 근처의 다른 실패로 대체하면 엉뚱한 버그를 고치게 된다. ② 결정적일 것 — 비결정 버그면 재현율을 디버깅 가능한 수준까지 올리고 그 재현율을 적는다.
     - `진단 + red 불가`. 원인은 아는데 실행 가능한 재현 명령이 안 나오는 경우다. `원인 미상`과 다른 상태이고 진단 실패가 아니다. 둘 다 갖춰야 이 라벨을 쓴다. ① 불가 사유가 이 부류에 속할 것 — 기기 의존 / 비결정(재현율을 못 올림) / 시각·렌더링 / 프로덕션 데이터 의존 / 외부 서비스 의존. 부류 밖이면 red를 만들 수 있다는 뜻이니 만들어라. ② 대체 증거를 붙일 것 — 실기기 로그, 패킷 캡처, 프로덕션 스택트레이스, 화면 녹화처럼 실제로 관측한 출력. 사유만 있고 대체 증거가 없으면 `원인 미상`이다.
     - `원인 미상 — 증상 완화`. 사슬이 끊겨 원인을 모르는 경우. 사용자에게 알린다.
     - 라벨은 아래로 흐른다 — 5단계 완료 기준의 형태와 review의 확인 방식이 이 라벨로 갈린다.
   - **증거는 증상을 고정할 뿐이다 — 원인은 사슬로 끝까지 판다.** 어느 라벨이든 증거가 잡아주는 건 "이 증상이 실재한다"까지고, "무엇이 원인인가"는 아직 열려 있다. 증상에서 "왜?"를 이어 붙여 **사슬로** 적는다(`증상 ← A ← B ← 뿌리`). 첫 번째 그럴듯한 층에서 멈추지 마라 — 거기가 근인(proximate cause)이고, 그것만 고치면 **같은 뿌리에서 다른 증상이 다시 난다**. **멈춰도 되는 건 아래 셋에 닿았을 때뿐이다**:
     - ① 다음 "왜?"가 **우리가 못 고치는 영역**(펌웨어·OS·서드파티 SDK·외부 서버·타 팀 소유 코드)으로 넘어간다 → 거기서 멈추고 그 외부 동작을 **미해결·전제**에 올린다(ground truth 대조 필수 — self-check ③).
     - ② 다음 "왜?"가 **의도된 설계 결정**에 닿는다 → 그 결정이 원인이다. "그 결정을 바꿀 것인가"가 이 plan의 안건이 된다.
     - ③ 다음 "왜?"의 답이 안 나온다 → **진단 실패**다. 이때만 `원인 미상 — 증상 완화`로 가되, **어느 고리에서 끊겼는지와 무엇을 시도했는지**를 함께 적는다. 그리고 완화가 **원인 관측을 가리지 않는지** 확인한다 — 증상을 삼키면 다음 진단이 불가능해진다.
   - **마지막 고리의 인과는 따로 확인한다.** "증상이 재현된다"는 상관관계고 "이 고리가 원인이다"는 **인과** 주장이라 층이 다르다 — 증상 증거가 사라지는 것만으로는 뿌리를 고친 건지 근인을 때운 건지 구분되지 않는다. 확인 방법은 **그 고리를 되돌리면 증상이 나고 고치면 사라지는지**다(실행 못 하면 추론으로라도 근거를 적는다). 확인 못 한 고리엔 **`(가설)`을 붙이고 미해결·전제로 올린다** — 근거 없는 고리 위에 세운 접근은 그 고리가 틀리면 통째로 무효이므로, 무효가 되는 범위를 그 전제 옆에 적는다.
   - **기능류 — 요구의 출발점을 적는다.** 해결하려는 실제 문제 한두 줄(동기·트리거). 요청이 이미 해법 형태로 오면("X 버튼 추가해줘") **그 해법이 그 문제를 푸는지부터** 확인한다 — 출발점 문제가 아니라 그 증상만 덮는 거면 그 지점이 대화 안건이다(self-check ④가 다시 묻는다). 대화에서 증발할 맥락을 파일에 보존하는 게 목적이다.
   - **기능류 — 새 동작이 기존 동작과 부딪히는 지점을 찾는다.** 요청은 새 동작만 말하고, 그 동작이 건드리는 기존 자동 처리(연쇄 호출·상태 전이 훅·알림·정리·대기열·예약 작업)는 말하지 않는다. 새 동작이 쓰거나 바꾸는 상태마다 **그 상태를 읽거나 그 변화에 반응하는 기존 코드를 Grep으로 찾고**, 겹치는 지점마다 "이 기존 동작이 새 경로에서도 그대로 도는 게 맞나?"를 판정한다. 셋 중 하나다.
     - ① 코드·문서·사용자 말로 답이 이미 정해져 있다 → 영향 범위에 적고 묻지 않는다.
     - ② 정해져 있지 않고 결과가 사용자 눈에 보인다(돈·권한·다른 사용자에게 가는 효과·데이터 보존·자원 점유) → **정책 결정이다.** 권장 답과 함께 질문으로 올리고 미해결·전제에 `(정책)`으로 적는다.
     - ③ 정해져 있지 않지만 바꿔도 사용자가 신경 쓰지 않는 값(재시도 횟수·타임아웃 기본값) → 기본값을 적고 끝낸다.
     - 막으려는 실패는 ②를 "기존 동작 재사용"으로 조용히 채우는 것이다 — **기존 코드를 재사용하는 건 구현 결정이지 정책 결정이 아니다.** 재사용하면 그 정책을 새 경로에도 적용한다는 뜻이고, 그게 맞는지는 사용자가 정한다. (실측: 예약 취소 요청에서 취소가 대기자 자동 승격을 일으킨다는 걸 코드로 파악하고도 3 run 모두 "기존 승격 로직 그대로"로 정했다. 결제 기한 없는 승격 예약이 자리를 묶는 문제는 사용자가 정할 일이었다.)
     - 사실은 여전히 묻지 않는다. "승격이 일어나나요?"는 코드가 답한다 — 묻는 건 "승격시킬까요?"다.
   - **구조 기준은 넷이고 앞이 우선한다** — ① done됐지만 아직 `ARCHITECTURE.md`에 반영되지 않은 구조 plan(아래 `ARCHITECTURE.md 미반영` 규칙 — 문서보다 새 결정이다) ② repo 루트 `ARCHITECTURE.md` ③ 실측한 기존 관례(이 repo, 또는 사용자가 지목한 다른 프로젝트) ④ 플러그인의 **범용 구조 규칙** — `${CLAUDE_PLUGIN_ROOT}/reference/structure-rules.md`(규칙 18개)와 그 세부 `structure-guide.md`(같은 폴더, §1–§18).
     - ④는 앞의 셋이 답하지 않는 곳에만 적용한다: `구조 관례: 신규`, 앞의 셋이 답하지 않는 경계(예: `ARCHITECTURE.md`가 의존 방향만 정하고 수명 정책은 비어 있음), 구조 plan이 목표 상태의 기준으로 명시적으로 채택한 경우.
     - **구조 plan은 현재와 목표를 나눈다.** 현재 상태 실측(자원 목록의 현재 위반)은 ①–③을 기준으로 하고, 목표 상태의 기준은 `구조 기준:`에 직접 고른다(기존 관례 유지 / 범용 채택). 범용을 채택한 목표는 그 구조 plan의 범위에만 적용되고, done 전에는 다른 feature plan의 기준이 아니다. 앞의 셋을 따르는 feature plan에서 ④와 다른 점은 **위반이 아니다** — 이 feature가 그 지점을 건드리면 아래 "feature 중 드러난 기존 구조 변경"의 근거로, 아니면 `미해결·전제`의 발견 사항으로만 적는다. 그렇게 하지 않으면 기존 repo의 모든 feature plan이 리팩터링이 된다.
     - **④를 적용하면 구조 축을 채우기 전에 `structure-rules.md`를 전부 읽고**, 그 문서 끝의 "읽을 때" 표에 걸리는 `structure-guide.md` 절을 읽는다. 기억이나 요약으로 대신하지 않는다.
     - `## 구조` 첫 줄에 `구조 기준:`을 적는다. 출처가 여럿이면 출처마다 맡는 범위를 괄호로 붙여 나열한다 — `구조 기준: ARCHITECTURE.md(의존 방향) + 범용 — R9, R11, §16(BLE 소유자 수명)`. 범용이 들어가면 이 변경이 기대는 규칙 번호를 인용한다 — build와 review가 같은 규칙을 보는 근거가 이 줄이다. 구조 영향이 없는 변경(문구·상수·단일 파일 내부)이면 `구조 기준: 해당 없음 — <이유>`로 끝내고 출처 선정과 문서 읽기를 건너뛴다.
   - **`ARCHITECTURE.md`가 구조 규칙의 1차 출처다.** repo 루트에 있으면 구조 축을 채우기 전에 먼저 읽는다(`구조 기준: 해당 없음`이면 건너뛴다) — 거기 적힌 규칙과 경쟁하는 규칙을 코드에서 따로 추론하지 않고, `구조 관례:`·`구조 규칙:`은 그 문서를 가리킨다. 이 변경이 거기 적힌 규칙을 바꿔야 하면 구현 세부가 아니라 아래 "feature 중 드러난 기존 구조 변경" 절차다(조용히 흡수하지도, plan 안에서 문서를 고치지도 않는다). **없을 때 만들지 않는다** — 구조 plan이 done이 되거나 같은 경계를 plan마다 다시 실측하고 있다면 review의 학습 제안(review 6단계)으로 **가장 작은 초안**을 제안할 뿐이다. **문서에 아직 반영되지 않은 done 구조 plan이 이 문서와 다르면 그 구조 plan이 우선한다**(승인된 갱신이 실제로 문서에 반영된 뒤에는 문서가 기준이다) — 문서 반영은 학습 제안 승인을 기다리므로, 그 사이 불일치는 `미해결·전제`에 `ARCHITECTURE.md 미반영: <규칙>`으로 적는다. 이 문서는 아키텍처 설명서가 아니라 짧은 불변식 목록이다(규칙마다 검증 수단 — 적합도 함수 이름, 없으면 `review` — 과 알려진 위반 포함). 범용 규칙을 적용한 프로젝트면 `structure-guide.md` §13의 항목(기능 경계와 공개 API, 의존 규칙, 소유자 표, Coordinator 정책 표)이 그 목록이다 — 범용 규칙 자체를 옮겨 적지 않는다. `.plans/`가 ignore돼도 남아야 하는 구조 규칙의 영속 위치가 여기다.
   - **구조 plan 분리 판정** (수정류·기능류 공통, 안건 확정 직후 한 번). 아래 둘 다 참이면 이 안건을 바로 plan하지 말고 **구조를 먼저 별도 안건으로 돌린다**(`.plans/<slug>-structure/`).
     - ① **관례를 실측할 참조 대상이 없다** — 이 repo에도, 사용자가 지목한 다른 프로젝트에도. **있으면 그걸 실측해서 `구조 관례: 따름`으로 끝낸다** — 새 repo라도 같은 팀의 다른 앱이 있으면 관례는 이미 서 있다. 진짜 greenfield는 드물다.
     - ② **새로 세우는 레이어·모듈이 2개 이상**이다. 하나면 `새 경계` 조건부 축으로 충분하다.
     - 이유는 크기다. 축 한 칸에서 모듈 여러 개·포트·에러 정책·상태 모델을 한 번에 결정하게 된다. 안건 하나 = plan 하나가 이 루프의 단위이므로 구조는 자기 plan을 갖는다.
     - **기존 모듈 점검도 구조 plan이다.** 사용자가 이미 있는 모듈의 구조 점검·재정비를 요청하면("X 구조 점검하자 / 구조 다시 잡자") 위 ①② 판정 없이 구조 plan을 연다. **범위는 모듈 하나** — 앱 전체 점검은 모듈별 plan으로 쪼갠다. 이 진입점이 없으면 구조는 feature plan을 따라 조각조각 생기고, 조각 사이의 규칙(누가 무엇을 소유하나)은 어느 plan의 안건도 되지 않는다.
     - **feature 중 드러난 기존 구조 변경은 사용자가 고른다.** 이 feature가 **기존 구조 규칙을 바꾸거나 새로 세워야** 하면(소유자 신설·의존 방향 변경·모듈 간 책임 이동) 판정 규칙으로 정하지 말고 **두 선택지를 `흐름 비교`(구조 축)와 함께 제시**한다 — ⓐ feature plan 안의 공유분 task로 둔다 ⓑ `<slug>-structure` 구조 plan으로 먼저 뺀다. 권장안은 달되 자동으로 고르지 않는다. 규칙 대신 그림인 이유: 경로 이전은 거의 항상 호출부 단위로 쪼개 매번 green을 낼 수 있어서 "green이 되나" 같은 기준은 걸리지 않는다 — 규모와 범위는 흐름 몇 개가 어느 레이어에서 경로를 바꾸는지로 보이고, 그건 사람이 판단할 것이다.
       - ⓑ가 선택되면 ① feature plan을 `status: on-hold — <slug>-structure 대기`로 두고(초안 단계면 저장하지 않고 대화에만 남긴다) ② 구조 plan을 기존 모듈 점검 경로로 연다 ③ 구조 plan이 done이 되면 feature plan을 **새 버전**으로 재개한다 — `구조 관례: 따름`, `구조 규칙: 위반 0곳 | 강제: <이름>`.
       - **이렇게 연 구조 plan의 범위는 이 feature가 건드리는 자원까지다.** 자원 목록도 그 자원만 적고, 같은 모듈에서 발견한 다른 위반은 `미해결·전제`에 발견 사항으로만 남긴다(흐름 비교의 EXTRA와 같은 내용). 모듈 전체 점검은 사용자가 "구조 점검"으로 따로 연다 — 안 그러면 분리를 고르는 순간 범위가 모듈 전체로 불어나 비교 그림이 보여준 범위와 실제 plan이 어긋난다.
     - **구조 plan의 본문 — 구상은 동인에서 시작한다.** 새 경계 축(층·방향·강제)에 앞서 셋을 적는다. 기존 모듈이면 셋 다 **현재 상태의 실측**에서 출발한다.
       - ① **동인** — 이 모듈이 반드시 잘해야 하는 품질 속성 2~3개를 **측정 가능한 시나리오**로: `<자극> → <기대 반응> (<측정: 수치·조건>)`. 예: `연결 중 링크 끊김 → 5초 안에 재연결, 진행 중 GATT 요청은 실패로 반환 (fake 링크로 테스트)`. 측정할 수 없는 형용사("안정적·확장 가능")는 동인이 아니다 — 쓰지 않는다. 형식적 한 줄로 채워지는 칸은 체크리스트 전체의 신뢰도를 떨어뜨린다.
       - ② **자원 목록** — 모듈이 다루는 상태·부작용 있는 공유 자원 **전부**(feature에서 분리한 구조 plan은 그 feature가 건드리는 자원만 — 위 범위 규칙)를 표로: `자원 | 소유자 | 실행 컨텍스트 | 정리 책임 | 현재 위반(Grep 실측, 검색 명령 포함)`. `구조 기준:`에 범용이 들어가면 `structure-guide.md` §13 소유자 표의 칸(생성·해제·공유 범위)을 더하고, 실행 컨텍스트 칸에 직렬화 경계를 적는다. 목표 기준이 현재 기준과 다르면 `목표와의 차이` 칸을 더한다 — 현재 기준으로는 위반이 아니지만 목표로 옮겨야 하는 것이다. feature plan의 `구조 규칙:`·`상태·실행 모델:` 줄을 모듈 전체에 한 번에 적용한 것이다 — 이후 feature plan은 이 표를 참조해 한 줄로 끝난다.
       - ③ **핵심 결정** — 동인마다 그것을 만족시키는 결정 + **버린 대안과 이유** 한 줄. **동인에 이어지지 않는 결정은 과설계 후보다** — 근거 없이 서는 추상·레이어를 여기서 걸러낸다.
     - **구조 plan의 완료 기준은 문서가 아니라 오라클이다.** ① **가장 얇은 수직 슬라이스 하나**를 최상단에서 **오라클이 닿는 최하단까지** 실제로 관통시키고 green — 그 아래(실기기·외부 서비스처럼 오라클이 못 닿는 경계)는 fake 어댑터로 끊되 **끊은 지점을 미해결·전제에 적는다**(구조가 증명된 범위가 어디까지인지 흐려지면 안 된다. 그 경계를 실제로 뚫는 것은 첫 feature plan의 우선 task이고, 거기서 `red 불가` 라벨이 붙을 수 있다). 포트와 배선은 진짜여야 한다 — fake로 끊는 건 어댑터 하나지 경계 자체가 아니다. **기존 모듈 점검이면 ① 대신 자원 목록의 현재 위반을 소유자로 모으는 task들**(목표 기준이 현재 기준과 다르면 `목표와의 차이`를 메우는 task들도 — 단독 green이 나면 둘을 다른 task로 나누고, 함께 바뀌어야 green이면 5단계 wide refactor 규칙대로 한 task로 묶되 현재 위반 정리와 목표 이행의 완료 기준은 각각 적는다)이 본문이다(한 번에 못 옮기면 5단계 wide refactor 분해를 따른다) ② **강제 장치가 정말 강제하는지 확인** — 방향을 어기는 import를 일부러 넣어 빌드가 깨지는 걸 본다. 깨지면 다이어그램이 희망사항이 아니라 사실이고, 안 깨지면 강제 장치가 없는 것이므로 `새 경계` 축의 답을 "관례뿐"으로 정정하고 미해결·전제로 올린다. **설계만 하고 짓지 않는 plan은 만들지 마라** — 검증 안 된 스캐폴드는 이 루프의 검증 바닥(오라클)을 어긴다. ③ **자원 목록의 소유·방향 규칙을 전부 적합도 함수로 건다** — 수단과 위반 주입 red 확인은 구조 축 `구조 규칙`과 같다. 적합도 함수 없이 표만 남으면 첫 급한 커밋에서 무너진다 ④ **동인 시나리오를 검증한다** — 테스트로 만들 수 있으면 테스트(fake 어댑터로 자극을 주입), 못 만들면(실기기·실시간) 수동 확인 절차와 **누가 언제 하는지**를 적는다.
     - 구조 plan이 done이 된 뒤의 feature plan들은 그 산출물을 실측해 `구조 관례: 따름`으로 가고, `구조 규칙:`은 자원 목록과 그 적합도 함수를 가리키는 한 줄(`위반 0곳 | 강제: <이름>`)로 끝난다. **greenfield 분기는 한 번만 겪는다.** 자원 목록과 규칙이 `.plans/` 안에만 있으면 ignore·정리와 함께 사라지므로, 구조 plan의 review에서 `ARCHITECTURE.md` 반영을 학습 제안으로 올린다. 새 불변식을 세우거나 바꾼 구조 plan이면 review 보고에 **구조 규칙의 영속 상태**를 한 줄로 적는다 — `기존 ARCHITECTURE.md에 반영 / 최소 초안 제시 / 보류 — 사유`. 사용자 결정은 기록하되 문서 작성을 accept의 조건으로 삼지 않는다(새 게이트가 아니다 — 제안이 처리됐는지를 보이게 하는 것이다). 영속되지 않으면 이후 plan마다 `구조 기준:`에 이전 plan들을 나열하며 구조를 다시 읽게 된다(실측).

2. **초안 작성.** 아래 상시 5축을 **반드시 명시 섹션으로** 다룬다. **제시하는 초안도 아래 `plan 파일 형식`의 `##` 헤딩을 그대로 쓴다** — 굵은 글씨·번호 목록으로 섹션을 대신하지 않는다. 승인되면 이 초안이 그대로 저장된다. 해당 없는 축은 "해당 없음 + 이유" 한 줄 — 빈 섹션도, 무단 생략도 금지. 이 체크리스트가 lens fan-out을 대체하는 바닥이다(대충 보는 날에도 축은 훑게).
   - **구조**: 변경이 어디에 어떻게 들어가나. 기존 경계를 따르나, 새 seam을 벌리나(벌린다면 왜 — 판정 기준은 **어댑터 수**다: 하나면 가상의 seam, 둘이면 진짜 seam. 프로덕션 구현 하나뿐인 포트는 추상이 아니라 간접층이고, build의 단순화 pass가 "불필요한 추상"으로 걸어낼 것을 애초에 안 만드는 것이다. **예외 둘. ①** 그 패턴이 repo에 이미 서 있으면 어댑터 수로 판정하지 말고 관례를 따른다 — 그건 새 seam을 벌리는 게 아니라 기존 경계를 따르는 것이고, 혼자만 다른 모양이 되는 비용이 간접층 비용보다 크다. **②** **IO·기기·외부 서비스 경계**(BLE·센서·네트워크·파일시스템·시계·결제사 등)는 **어댑터 수와 무관하게 seam을 만든다** — 여기서 포트의 존재 이유는 다형성이 아니라 **테스트 격리**이고, 그건 프로덕션 구현이 하나여도 유효하다. 이 예외가 없으면 IO 경계에 seam이 안 생겨 build의 고위험 표면 판정이 영구히 `안 닿음`이 되고 수정류 증거가 상시 `red 불가`로 떨어진다 — 두 규칙이 서로를 무력화한다. **이 예외로 만든 seam은 단순화 pass의 제거 대상이 아니다**(plan에 근거가 적혀 있으므로 제거는 이탈이다)). **유사 기존 구현을 확인했나** — 재사용/확장 대신 신규로 가면 그 근거.
     - **구조 관례**: `구조 관례: <따름 | 벗어남 — 이유 / 남는 불일치 | 신규 — 여기서 정한 관례>` 한 줄. **greenfield(따를 경계가 없을 때)는 `신규`다** — "따름"도 "벗어남"도 거짓이므로 억지로 고르지 말고, **이 변경에서 세우는 관례를 그 자리에 적는다**(어디에 무엇을 두고, 무엇을 무엇이라 부르고, 에러를 어떻게 다루는지, 경계를 건너는 흐름을 어떻게 로그로 남기는지). 새 경계 축이 트리거됐으면 거기서 정한 방향·강제 장치와 같은 내용이어야 한다. **`따름`은 이번 변경의 책임·자원·수명·의존을 기준 규칙이 실제로 덮을 때만 쓴다.** 새 책임이나 플랫폼 자원(파일시스템·네트워크·락·스레드·타이머) 호출이 생기면, 그것을 소유하는 규칙과 그 규칙을 거는 검사가 기준에 있는지 대조한다. 있으면 그 규칙을 가리키고 `따름`, 기준이 답하지 않는 부분은 그 부분만 `신규 — <정한 관례>`로 분리해 적고 아래 `구조 규칙`의 강제 절차(R18)를 적용한다 — 다이어그램에 없다는 이유만으로 신규가 되지는 않는다(새 helper·codec이 곧 새 소유자는 아니다). 이 대조가 없으면 기준이 덮지 않는 책임이 feature plan마다 `따름`으로 통과하며 규칙 없이 자란다(실측: 구조 plan 이후 영속 계층 전체가 `따름`으로만 생겼고, 그 fs 소유는 어느 검사도 보지 않았다). 사람이 diff를 못 따라가게 만드는 건 이탈 자체가 아니라 **기록 안 된 이탈**이다("여긴 왜 혼자 다르지"를 코드에서 역추적하는 순간 review 게이트가 형식이 된다). 벗어나는 건 금지가 아니다 — 맞지 않는 모양에 욱여넣으면 코드가 더 나빠진다. 기록하고 알리면 된다. 경계를 건너는 새 흐름을 만들면 **경계 로그 관례**(무엇을 어디서 남기나)도 이 줄에 포함한다 — 문제 위치를 좁힐 수 있는 건 경계의 입출력이 보일 때다. **이 줄이 task slice로 흘러가 builder가 새 파일에서도 관례를 따르는 근거가 된다**(builder는 slice만 보므로, 새 파일엔 따라 할 주변 코드가 없다).
     - **불변식**: 이 변경 후 **무엇이 항상 참인가**. 그리고 그걸 **타입으로 불가능하게 만들었나, 런타임 체크로 막았나** — 런타임을 골랐으면 왜 타입이 아닌지. 런타임 방어는 호출부마다 늘어나고 나중에 타입으로 옮기려면 전면 수정이다. 상태가 없는 변경(순수 추가·설정 값)이면 "해당 없음" 한 줄.
     - **구조 규칙**: 변경이 기대는 **기존 구조 규칙**을 적고 그 위반을 **Grep으로 실측**한다. 두 종류다.
       - *소유* — 상태·부작용 있는 공유 자원(concurrency·persistence·외부 I/O·전역/싱글턴 상태 — build 고위험 표면과 같은 분류)을 건드릴 때. 위반 = 소유자 밖에서 그 자원의 **원시 API**(플랫폼 SDK·드라이버·DB 클라이언트·전역 쓰기)를 직접 부르는 위치.
       - *방향* — 레이어·모듈 경계를 건너는 의존을 추가할 때. 위반 = 역방향 import.
       - 형식: `- <소유|방향>: <규칙> | 위반 N곳 (<검색 명령>) | 강제: <검사 이름 | 없음>`.
       - 이 변경은 규칙을 **따른다** — 위반을 하나 더 늘리는 설계면 그 이유 자체가 이 plan의 안건이다.
       - **위반이 있거나 강제가 `없음`이면 적합도 함수 task를 넣는다**: 위반을 규칙 쪽으로 모으고 규칙을 오라클에 건다. 수단은 **이미 있는 것 먼저**(repo의 아키텍처 테스트·lint 규칙·모듈 분리에 규칙 추가) → 없으면 **grep 테스트**(기존 테스트 러너에서 소스를 읽어 금지 패턴을 찾는 테스트 하나 — 언어 무관, 새 의존성 없음). **새 도구 도입(Konsist·ArchUnit 류)은 이 task에서 하지 않는다** — grep으로 못 잡는 위반(래퍼 우회·방향 규칙 다수)이 실제로 나왔을 때의 별도 plan 안건이다. 완료 기준은 수단과 무관하게 같다: 검사 green **+ 위반을 일부러 넣으면 red**(안 깨지면 강제가 아니다 — 구조 plan ②와 같은 확인). 검사마다 **적용 규칙 / 검사 경로·언어 / 허용 경로 / 알려진 사각지대**(탐지 방식이 못 잡는 형태 — 예: 경로 문자열 매칭이면 별칭 import)를 적는다. 규칙의 적용 대상인데 검사 경로에서 빠진 곳은 `미해결·전제`에 남긴다. 위반 주입 한 종류가 red였다고 검사 전체가 충분한 것은 아니다. 검사 범위를 넓힐 때는 새로 편입한 경로에서 위반 주입 red를 다시 본다. 이 기록은 검사마다 한 번, 범위가 바뀔 때만 갱신한다.
       - **`구조 기준:`에 범용이 들어가면 그 범위의 수단은 `structure-guide.md` §15 표를 따른다.** 강제 수단 칸에서 현재 구성에 맞는 수단으로 건다 — 빌드 모듈 하나면 import 검사 테스트, 나눈 모듈이면 모듈 의존성·접근 제어, 동작 규칙이면 테스트. grep 테스트는 보조 검사 칸의 규칙에만 쓴다. **강제 수단을 세우려는 이유만으로 빌드 모듈을 나누지 않는다** — 빌드 모듈 분리는 §14의 그 트리거가 참일 때만 별도 근거와 함께 task로 둔다. 언어 때문에 강제할 수 없는 규칙(Swift 단일 타깃의 Feature 내부 참조 등)은 `강제 수단 미적용: <규칙> — Swift 단일 타깃 / 리뷰로 확인`으로 적는다. 기존 코드라 강제 수단을 이번에 세울 수 없으면 grep 테스트를 임시 수단으로 걸고 `미해결·전제`에 `강제 수단 미적용: <규칙> — grep이 못 잡는 범위 / 옮길 시점`을 적는다.
       - 이유: 루트·역방향 의존이 늘어나는 침식은 경로 하나하나가 맞아서 오라클이 green이다 — 규칙을 오라클로 옮기기 전까지 어느 단계도 기계적으로 못 잡는다. 한 번 걸면 이후 plan은 `위반 0곳 | 강제: <이름>`으로 끝난다.
       - 공유 자원도 경계 이동도 없으면 이 줄을 쓰지 않는다.
     - **상태·실행 모델**: 상태를 보유하거나 비동기·생명주기가 있는 코드를 건드리면 한 줄 — `상태·실행 모델: 소유 <상태를 드는 컴포넌트> / 실행 컨텍스트 <스레드·큐·디스패처> / 정리 책임 <시작·취소·해제를 누가, 실패 경로 포함>`. 에러 정책과 같은 이유다 — 여기서 정하지 않으면 builder가 task마다 즉흥으로 고르고, 섞인 뒤엔 레이스·누수를 추적할 방법이 없다. 기존 모델을 따르면 그걸 적는다. 해당 없으면 쓰지 않는다. **락을 중첩해 잡거나, 락을 쥔 채 await·블로킹 I/O를 하는 경로를 만들면** 같은 줄에 획득 순서 / guard를 언제 놓는지 / 그 사이 허용되는 상태 변경을 적고, 역순 획득·재진입·지연 완료 중 해당하는 시나리오의 테스트나 검사를 완료 기준에 넣는다 — 순서가 정해져 있지 않으면 다음 호출자가 반대 순서로 잡아도 오라클은 green이다. 상태를 둘 이상 드는 것만으로는 해당하지 않는다.
     - 변경이 **2개 이상 레이어·모듈에 걸치면 ASCII 레이어 다이어그램**으로 그린다(단일 레이어면 생략 가능):
     - **레이어마다 테두리 박스**(`┌─┐` box-drawing), 박스 제목 = 레이어명. 플랫폼별 병렬 구현(Android/iOS 등)은 레이어 박스 안에 나란한 서브 박스. 레이어 간 흐름은 세로 화살표(`▼`)로, 크로스 언어·직렬화 경계는 화살표에 경계명 라벨.
     - 변경/신규 노드에 `*`. **전체 아키텍처 재현 금지 — 변경이 닿는 노드만.** **다이어그램 안 텍스트는 영어로만**(노드명은 어차피 코드 식별자, 주석도 `(new)` 식으로) — 한글 2폭 문자가 정렬을 깨는 유일한 원인이므로, 영문 전용으로 그리고 정렬은 정확히 맞춘다.
     - 이 다이어그램이 task 분해의 근거다: 공유 노드 = 공유분, 레이어를 가로지르는 흐름 = 병렬 주의.
     ```
     ┌────────────────────── UI LAYER ──────────────────────┐
     │  SettingsPage ──▶ SpeedVM*                           │
     └──────────────────────────┬───────────────────────────┘
                                ▼
     ┌──────────────────── DOMAIN LAYER ────────────────────┐
     │  SpeedVM* ──uses──▶ SpeedPolicy* (new)               │
     └──────────────────────────┬───────────────────────────┘
                                ▼
     ┌───────────────────── DATA LAYER ─────────────────────┐
     │  SpeedPolicy* ──reads──▶ PrefsRepo                   │
     └──────────────────────────┬───────────────────────────┘
                                ▼ MethodChannel("speed/config")*
     ┌──────────────────── NATIVE LAYER ────────────────────┐
     │  ┌─ Android (Kotlin) ──────┐  ┌─ iOS (Swift) ──────┐ │
     │  │ SpeedConfigHandler*     │  │ SpeedConfigHandler*│ │
     │  └─────────────────────────┘  └────────────────────┘ │
     └──────────────────────────────────────────────────────┘
     ```
     - **흐름 비교**: 변경이 **기존 호출 경로를 다른 경로로 돌리면**(소유자 신설·경유 강제 — 구조 변경 선택지 제시, 또는 `구조 규칙` 위반을 소유자로 모으는 task) 레이어 다이어그램 대신 **그 자원 하나의 데이터 흐름**을 BEFORE / AFTER로 그린다. 구조 변경을 판단하는 사람이 봐야 하는 건 "경로가 몇 개였고 몇 개가 되나"다.
       - 호출자는 `구조 규칙:`의 검색 결과에서 가져온다 — 기억으로 그리지 않는다. grep이 못 잡는 경로(콜백 등록·리플렉션)가 있으면 그림 아래에 그렇다고 적는다.
       - BEFORE에는 자원의 제약과 그로 인한 실패(재현했으면 그 결과), AFTER에는 새 소유자 노드 `*`.
       - 이 변경에 필요 없는데 같이 바뀌게 되는 흐름은 **EXTRA**로 따로 그린다 — 범위가 커지는 지점이 그림에서 보여야 한다.
       - **BEFORE / AFTER / EXTRA 제목 줄마다 한글 설명 한 줄**을 붙인다(`BEFORE — 경로 3개, 동시에 오면 하나가 버려짐`) — 무엇이 바뀌는지를 그림을 읽기 전에 알게 한다. 제목 줄은 뒤에 정렬할 문자가 없어 한글이 정렬을 깨지 않는다. 그 외 그림 안은 영문 전용·정렬 정확히(레이어 다이어그램과 같은 이유). 전체 아키텍처를 그리지 않는다.
     ```
     BEFORE — 경로 3개, 동시에 오면 하나가 버려짐
     UI        DetailVM ──read─────────────┐
     DOMAIN    FirmwareUpdater ──write─────┤
     DATA      ConnectionManager ──read────┤
                                           ▼
               ┌────────────────────────────────────────┐
     PLATFORM  │ BleStack: 1 op per link, 2nd dropped   │
               └────────────────────────────────────────┘
     AFTER — 경로 1개, 순서대로 하나씩
               (same 3 callers) ───────────┐
                                           ▼
               ┌────────────────────────────────────────┐
     DATA      │ GattQueue* (new owner, FIFO)           │
               └────────────────────┬───────────────────┘
                                    ▼
     PLATFORM                   BleStack
     EXTRA — 이 기능엔 필요 없지만 같이 바뀌는 것
     UI        PairingVM ──scan──▶ ScanController  (was: BleStack)
     ```
   - **의존성**: 이 변경이 무엇에 기대나 / 무엇이 이 변경에 새로 기대게 되나.
   - **영향 범위**: 수정이 닿는 파일·모듈·동작 + 직접 변경 밖 파급. **서술이 아니라 실측으로** — 시그니처·계약·동작이 바뀌는 심볼(함수/타입/스키마/설정 키/채널명)마다 사용처를 **실제 검색(Grep)으로 열거**한다. 기억·추정 금지. 많으면 개수 + 대표 예시 + 재현 가능한 검색 명령. 두 부류로 나눠 적는다:
     - *오라클이 잡는 파급*(타입된 호출부): 열거의 용도는 task 분해 — 담당 파일 목록에 반영.
     - ***오라클이 못 잡는 파급***: 문자열 키(라우트·이벤트·DI 등록명), 직렬화 포맷·저장 데이터, 리플렉션, 크로스 언어 경계(MethodChannel 등), 외부 API 소비자. 조용히 깨지는 부류다 — 잠재 에러 축으로 넘겨 검증 방법까지 단다.
     - **열거된 사용처가 넓게 퍼지면** 그건 공유분 task 하나가 아니다 — 5단계의 **wide refactor** 분해로 넘긴다. 판정 기준은 개수가 아니라 **한 변경이 여러 파일을 동시에 red로 만들어 단일 task로는 green을 못 만드는가**다. 공유 심볼 제거·재타이핑, enum/sealed 항목 추가로 exhaustive 소비자가 전부 깨지는 경우가 여기 든다 — 호출부가 열 개여도 해당한다.
     - 기존 심볼 변경이 없는 순수 추가 변경이면 "사용처 열거 해당 없음" 한 줄(blanket call-graph 조사 금지 — 깊이는 변경 심볼에만).
   - **잠재 에러**: 실패 경로·엣지·경계값·동시성. "무엇이 깨질 수 있나"를 구체 시나리오로(추상 명사 나열 금지). **항목마다 검증 방법과 대응을 붙인다** — `<시나리오> — 검증: <테스트/수동/미검증> / 대응: <어디서 잡고 무엇을 하나>`. "미검증"도 유효한 답이다 — 숨기는 것만 금지.
     - **고위험 표면(권한·schema/persistence·concurrency·자원 한도·되돌리기)을 건드리면 위험 패턴 카탈로그(`${CLAUDE_PLUGIN_ROOT}/reference/risk-patterns.md`)에서 트리거에 걸리는 패턴만 골라** 항목으로 적는다 — 패턴마다 `<실제 호출 경계> + <테스트 이름>` / `미검증` / `해당 없음 — 이유`. 전 패턴을 기계적으로 채우지 않는다(형식적 "해당 없음"이 늘면 체크리스트가 신뢰를 잃는다). 카탈로그는 리뷰가 실제로 잡은 결함 부류를 plan으로 당겨 오는 것이지 완전성 보증이 아니다.
     - **대응은 정책이지 개별 판단이 아니다.** throw / Result 반환 / 로그 후 degrade / 재시도 중 무엇인지, 그리고 **어느 층에서 잡는지**를 적는다. 항목마다 다른 방식이 섞이면 나중에 통일하려면 전 호출부를 건드려야 하고, 그 전에 이미 "이 에러가 어디서 잡히는지 아무도 모르는" 상태가 된다 — 이 축에서 정하지 않으면 builder가 task마다 즉흥으로 고른다.
   - **범위**: 요청 대비 이 plan이 큰 곳(요청 안 한 추상·기능)과 작은 곳(요청의 핵심인데 빠진 것). 양방향, 2~3줄로 가볍게.

   **조건부 축** — 트리거될 때만 섹션을 추가하고, 아니면 섹션 자체를 생략한다("해당 없음" 표기도 하지 않는다 — 상시 축과 규칙이 다르다. 매 plan에 빈 섹션 4개를 만들지 않기 위함):

   | 축 | 트리거 |
   |---|---|
   | **보안** | auth·입력 처리·권한·민감데이터를 건드릴 때 |
   | **롤백·마이그레이션** | schema/persistence 변경·배포 영향이 있을 때 |
   | **성능·비용** | hot path·대량 데이터·자원 제약 경로일 때 |
   | **테스트 가능성** | side-effect·시간·IO·전역상태 결합이 미해결로 남을 때 |
   | **새 경계** | 기존 구조에 레이어·모듈을 새로 세울 때. **1단계 구조 plan 분리 판정의 ①②가 둘 다 참이면(참조할 관례가 없고 2개 이상) 구조 plan으로 가고, 이 축이 그 구조 plan의 본문이 된다.** 관례가 있으면 개수와 무관하게 이 축에서 그 관례를 따라 적는다 |

   **새 경계** 축은 세 가지를 적는다 — ① 층이 무엇 무엇인가(구조 축의 ASCII 다이어그램으로 갈음 가능) ② 의존이 어느 방향으로 흐르나 ③ **그 방향을 무엇이 강제하나** — import 검사 테스트 / lint 규칙 / 빌드 모듈 분리(§14 트리거가 참일 때만) / **아무것도 없고 관례뿐**. 셋째가 핵심이다: 강제 장치 없는 레이어링은 명명 규칙이고, 명명 규칙은 첫 급한 커밋에서 무너진다. "관례뿐"도 유효한 답이지만 그러면 그게 **미해결·전제**로 올라간다(무너질 것을 알고 시작하는 것이다). 패턴 이름(Clean Architecture·MVI 등)을 적는 것으로 이 축을 대신하지 마라 — 이름은 검증 가능한 답이 아니다.

3. **출력 전 self-check.** 여섯 가지를 확인한다.
   ① 상시 5축이 실제 내용으로 채워졌나. 조건부 축 트리거를 놓치지 않았나.
   ② 전체 재독 — 섹션 간 자기모순이 없나.
   ③ 틀리면 접근이 무너지는 전제가 "미해결·전제"에 있나. 그중 코드 밖 사실(펌웨어·OS·SDK·외부 서버·타 팀 동작)은 승인 전에 ground truth로 대조하고 출처(로그·캡처·실기기·문서)를 적는다. 틀린 외부 전제 위에서도 오라클은 전부 green이므로 여기가 유일한 검증 지점이다. 대조 못 했으면 `검증 필요`와 함께, 무너지면 무엇이 버려지는지 한 줄.
   ④ (수정류) 원인 사슬이 정지 조건 ①②③ 중 하나에 닿았나, 접근이 마지막 고리를 제거하나. 기본은 뿌리다. 근인에서 고치기로 했으면 `## 접근` 맨 위에 `수정 지점: <고리> — 뿌리가 아닌 이유 / 남는 부채`를 적고 제시할 때 사용자에게 한 줄로 알린다. 부채는 미해결·전제가 아니라 접근에 적는다 — 틀릴 수 있는 것과 알면서 남기는 것은 다르다. (기능류) 요청받은 해법이 출발점 문제를 실제로 푸나. 새 동작이 부딪히는 기존 동작을 Grep으로 찾았나, 그중 정책 결정(1단계 ②)을 "기존 동작 재사용"으로 조용히 채운 곳이 없나.
   ⑤ 지시가 두 갈래 이상으로 읽힌 지점에서 한쪽을 골랐다면 "미해결·전제"에 `(해석)`으로 선언했나. 없으면 없다고 넘어간다.
   ⑥ (`구조 기준:`에 범용이 들어갈 때) 이 plan이 범용이 맡은 범위 안에서 새로 만드는 §14 표의 항목(Domain·입출력 계약·Controller·사용권·Coordinator·공개 사실 스트림·Feature·영역 묶음)마다 `structure-guide.md` §14 트리거와 근거 한 줄이 `## 구조`에 있나(R17). 근거를 못 적은 것은 빼고 다시 제시한다 — 범용 규칙을 적용할 때 가장 흔한 실패는 규칙이 허용한 분리를 트리거 없이 미리 만드는 것이다.

4. **제시 → 수정 → 반복.** 사용자 수정 지시를 반영해 다시 제시한다. 사용자가 **명시적으로 승인**할 때까지. **승인 전 코드 수정 금지.** roadmap에 사용자의 plan 승인 위임 원문이 기록돼 있으면 그 범위 안에서는 메인이 self-check를 통과한 plan을 승인하고 진행한다 — 위임 밖의 결정(`(정책)` 질문 포함)이 남으면 사용자에게 묻고 그 plan은 대기한다.
   - **한 라운드에 물을 수 있는 걸 다 묻는다.** 질문마다 번호를 붙이고 **각 질문에 권장 답을 함께 단다** — 동의하면 "다 ok" 한 마디로 라운드가 닫히고, 반대할 때만 타이핑하게 된다. 왕복 횟수가 아니라 왕복당 사용자 부담을 줄이는 것이다.
   - **아직 열려 있는 다른 질문의 답에 의존하는 질문은 이번 라운드가 아니라 다음 라운드다** — 안 그러면 답을 추측한 채로 묻게 된다. 사실은 묻지 않고 결정만 묻는다(1단계 규칙 그대로).
   - 승인과 함께 진행 지시가 오면("승인, 바로 진행해" 류) 저장(5) 후 **별도 호출 대기 없이 Skill 도구를 `jay-flow:build`로 호출한다** — "build로 이어간다"고 산문으로 적지 말고 도구 이름을 짚어라(지시가 서술로 읽히면 연속 주행이 끊긴다). 사람 게이트는 plan 승인과 review 판정 둘뿐, 그 사이는 연속 주행이다.

5. **승인 시 task 분해 + 저장.** `.plans/<slug>/v1.md`로 저장:
   - 각 task: 무엇을 / 참조할 plan 섹션(slice) / **담당 AC** / **예상 담당 파일** / 완료 기준(가능하면 오라클 — 어떤 테스트·타입체크·빌드가 green이어야 하나). **모든 AC가 최소 한 task의 완료 기준에 매핑돼야 한다** — 매핑 안 된 AC는 아무도 확인하지 않는다. 담당 파일은 build가 병렬 가능(파일 disjoint) 여부를 판정하는 근거다. **영향 범위에서 열거한 사용처 수정도 task에 포함**하라 — 담당 파일 목록의 정확도가 병렬 판정의 정확도다.
   - **task는 독립적으로 검증·롤백할 수 있는 기능 단위다.** 내부 helper·좁은 API 한 단계·테스트 보강만으로 task를 나누지 마라 — task마다 builder 문맥 재구성·전체 오라클·판정·체크포인트가 붙으므로, 소비자 없는 중간 단계를 task로 쪼개면 그 고정 비용이 단계 수만큼 곱해진다. 순수 모델과 그것을 처음 쓰는 경로는 한 task로 묶는다. 반대로 권한·저장·실패 원자성처럼 실패 의미가 다른 책임은 한 거대 task로 합치지 않는다.
   - **담당 파일은 producer → adapter → caller → 테스트·fixture → 저장 소비자를 따라 대조한다.** 영향 범위 열거가 심볼 사용처만 보면 그 심볼을 화면에 표시하는 컴포넌트·그 경로를 마운트하는 기존 테스트가 빠진다 — 빠지면 builder가 담당 밖 수정에서 멈추고 task가 통째로 재시작된다(실측: GUI 소비자 컴포넌트와 그것을 마운트하는 기존 테스트가 연달아 빠져 같은 task가 두 번 중단됐다).
   - 공유 타입·스키마·계약처럼 다른 task가 기대는 것 먼저 — 이건 "공유분"으로 표시(build가 순차로 먼저 처리). **구조 규칙 적합도 함수 task도 공유분이다** — 기능 task가 그 규칙 위에 서므로 위반 정리와 강제 검사가 먼저 선다.
   - **wide refactor는 공유분으로 묶지 마라.** 한 기계적 변경의 blast radius가 호출부 전체로 퍼지는 것(공유 심볼 재타이핑, 컬럼 rename 등)은 **단일 task로 오라클 green이 안 나온다** — 호출부가 몇 개든 한꺼번에 깨지면 해당한다. **expand → migrate → contract**로 쪼갠다: ① **expand** — 새 형태를 구 형태 옆에 추가(아무것도 안 깨진다) ② **migrate** — 호출부를 패키지·디렉터리 단위 배치로 이전, **배치마다 별도 task이고 배치마다 green**(구 형태가 살아 있으므로 가능하다) ③ **contract** — 남은 호출부가 없을 때 구 형태 삭제. 배치 단독으로 green이 안 되는 경우에만 그 배치들을 **한 task로 묶는다** — 묶은 task 하나가 green을 약속하고, 중간에 red인 task를 따로 두지 않는다(build는 task마다 green을 요구하므로 중간 red task는 repair·에스컬레이션에 걸려 진행이 멈춘다). 두 가지를 놓치기 쉽다. **exhaustive 소비자**(전수 분기 + `assert_never`류)가 있는 public enum/sealed에 항목을 추가하는 것은 expand가 아니다 — 추가하는 순간 소비자 전부가 동시에 깨지므로, 그 소비자 파일 전부를 한 task로 묶거나 진단·부가 정보는 별도 채널(콜백·internal 타입)로 뺀다. contract 단계의 파일 목록에는 **non-owned 테스트·sample·예제 소비자**도 들어간다 — 구 API를 참조하는 것은 전부 grep으로 열거한다. **contract를 이 plan에서 하지 않고 넘기면** `미해결·전제`에 `남은 contract: <제거 대상 API·writer·호출자> — <담당 plan | 종료 조건>`을 적는다. 승인된 호환 reader·bridge·구성 모델은 제거 대상이 아니다 — 구 형태가 남아 있다는 사실만으로 제거를 요구하면 데이터 호환성을 깬다. 안 적으면 expand·migrate만 하고 끝난 구 형태가 어느 plan의 안건도 되지 않는다.
   - **수정류 완료 기준은 1단계 라벨을 따른다.**
     - `진단 + red` → 그 red의 **red→green을 우선 포함**. 다만 그건 **증상**에 assert하므로 뿌리를 고쳐도 green, 근인만 때워도 green이다 — 근인 패치를 걸러내지 못한다. 그래서 **수정 지점이 뿌리면 뿌리의 계약에 직접 거는 테스트를 하나 더** 넣는다(뒤에 누가 근인만 때우면 red가 나야 한다). 수정 지점이 근인이면 1단계 red 하나로 족하다 — 뿌리를 안 고치기로 한 것이고 그 사실은 `수정 지점`에 이미 적혀 있다.
     - `진단 + red 불가` → **대체 증거의 재관측**을 완료 기준에 적는다: 같은 로그·캡처·스택트레이스를 **같은 절차로 다시 떠서** 증상이 사라졌는지. 절차를 그대로 쓴다(무슨 기기·무슨 조작·무엇을 볼지). 자동 오라클이 아니므로 **누가 언제 확인하는지까지** 적는다 — 안 적으면 아무도 안 한다.
     - `원인 미상` → 완화가 동작함만 확인할 수 있다. **원인 제거를 증명하지 않는다**는 사실을 완료 기준에 명시한다.
   - task 목록은 체크박스. **최신 버전 파일이 유일한 상태다** — 별도 state 파일 없음(아래 roadmap은 plan 사이의 순서·위임 기록이지 task 상태를 들지 않는다).
   - `.plans/`를 이 repo에 처음 만드는 거면 `.gitignore`에 `.plans/`가 있는지 확인하고, 없으면 사용자에게 한 줄로 묻는다(ignore할지 / 커밋에 실을지). 임의로 추가하지 않는다.

## 버전 규칙 (추적 가능성)

- **계약 변경 = 새 버전.** 목표·AC·승인된 동작 계약·공개 계약·schema·권한 의미·검증 의무가 바뀌거나 task가 추가·삭제되면(사용자 수정 지시, build 중 발견) 파일을 편집하지 말고 `v2.md`, `v3.md`…로 새로 만든다. 맨 위에 `변경: <무엇을 왜>` 한 줄 + 이전 버전의 task 완료 상태 이월. 새 버전 본문에는 **현재 유효한 계약만** 적는다 — 대체된 설명·교정 경위를 본문에 남겨 두면 최신 파일 안에서 무엇이 현재 계약인지 식별할 수 없게 된다(이력은 이전 버전 파일이 갖는다). **이전 버전 파일은 절대 수정하지 않는다** — 그게 이력이다.
- **소유 보정 ≠ 버전.** 기존 AC를 구현하는 데 필요한데 담당 파일에서 빠진 caller·테스트·fixture를 추가하는 것은 계약 변경이 아니다 — 최신 버전 하단 `## 소유 보정`에 `- <파일> — task N, <왜 필요한지 한 줄>`로 append한다. 새 동작·계약·schema·권한이 따라 들어오면 소유 보정이 아니라 새 버전이다. 이미 담당인 파일 안의 테스트 하네스 교정은 소유 보정조차 아니다.
- **실행 상태 갱신 ≠ 버전.** task 체크박스·status, 그리고 review가 done 때 덧붙이는 `## 리뷰 기록`(남은 advisory)은 내용이 아니라 실행 기록이다 — 최신 버전에 in-place로 갱신한다. 그 위의 plan 섹션은 고치지 않는다(`## 소유 보정`은 append만). 실패 출력·교정 가설·agent 수거 같은 **실행 사건은 plan에 쌓지 않는다** — 사용자에게 보고하고 끝내고, roadmap 위임 중이면 roadmap의 실행 기록에 남긴다. 예외는 위 `## 리뷰 기록` 한 번뿐이다(다음 작업의 씨앗). (실측: 안건 하나가 실행 사건마다 버전을 올려 21버전·394줄이 됐고, 그중 테스트 하네스 몇 줄 교정과 소유 파일 추가만으로 생긴 버전이 다수였다.)
- **유효본 = 최고 버전 번호.** build·review는 항상 최신 버전만 따른다.

## roadmap (여러 안건을 묶는 위임 주행)

사용자가 **여러 plan에 걸친 범위를 한 번에 위임**할 때만 쓴다("Phase 2~4 알아서 진행해", "자리 비우는 동안 남은 것 순서대로" 류). jay-flow가 스스로 자율 주행을 여는 장치가 아니다 — 사람 게이트(plan 승인·review 판정)를 사용자가 **명시적으로 위임**했을 때 그 위임의 범위와 순서를 기록하는 문서다. 위임이 없으면 만들지 않는다.

`.plans/<roadmap-slug>/roadmap.md` 하나(버전 파일 아님 — 실행 상태 문서다). 개별 task 상태의 권위는 각 plan의 최신 버전에 있고, roadmap은 그것을 참조만 한다(상태를 복제하면 둘이 어긋난다).

1. **최종 계약 먼저.** 위임 범위의 끝 상태가 기대는 계약(데이터 모델 식별·revision·영속 형식·트랜잭션·권한 경계 등)을 목록으로 적고, **그 계약을 소비하는 순서로** plan을 배치한다. 중간 모델로 저장·네이티브·GUI까지 완성한 뒤 최종 모델로 다시 이전하는 경로는 기본 순서가 아니다 — 꼭 필요하면(기존 사용자 데이터 보존 등) 이전 경로와 유지 이유를 적는다. 미래 요구 전체를 상세 설계하라는 뜻이 아니다 — 후속 plan들이 반복해서 소비할 계약만 먼저 고정한다. (실측: 중간 문서 모델 위에 레이어 저장·네이티브·GUI를 완성한 뒤 정식 모델로 이전하면서 저장 형식이 2→3→4로 바뀌고, 후속 단계를 여는 트랜잭션·journal은 위임 시간 안에 착수하지 못했다.)
2. **의존경로와 review 단위.** plan 간 의존(무엇이 무엇을 기다리나)과 critical path(위임 범위의 끝을 여는 계약까지의 경로)를 적는다. review는 **기능 단위 — plan 하나의 build가 끝났을 때**이고, task마다 붙이지 않는다. 공유 계약을 만든 plan은 그 계약을 소비하는 다음 plan 착수 전에 review를 끝낸다.
3. **위임 범위.** 사용자가 위임한 것(plan 승인 / review accept / 체크포인트 커밋)과 위임하지 않은 것(push·배포·유료 호출·credential·사용자 데이터)을 사용자 원문 그대로 적는다. 위임된 accept라도 review가 고위험 표면 `안 닿음`·`얕음`을 보고했거나 실제 결함을 찾았으면 수정·재리뷰 전에 accept하지 않는다.
4. **시간 예산.** 종료 시각이 있으면 착수 전에 **예상 완료 범위와 불확실성을 사용자에게 먼저 보고한다** — 사용자가 범위를 조정할 수 있는 마지막 순간이다. 추정 근거가 없으면 "추정 불가"라고 적는다(근거 없는 낙관 금지). plan 하나가 끝날 때마다 실제 소요로 재추정해 적는다. 남은 시간이 다음 plan의 구현·검증·review·교정·안전 정리를 담기 부족하면 새 plan을 시작하지 않고 검증된 상태와 미완료 계약을 인계한다.
5. **실행 기록과 학습.** `## 실행 기록`에는 plan 착수·종료, review 발견 분류(제품 결함 / 검증 보강 / 하네스 / plan 전제 오류), 소유 보정, 재추정만 짧게 append한다 — 커밋·세션 로그에서 다시 뽑을 수 있는 것은 쓰지 않는다. `## 학습`에는 다음 task에 재사용될 검증된 지식(테스트 환경 초기화 관례, 실측으로 교정된 전제 등)을 근거 위치와 적용 조건과 함께 적고, build는 관련 항목을 builder dispatch에 넣는다. 학습 항목은 새 계약이나 권한을 만들지 않는다. repo 문서로 옮기는 것은 사용자 복귀 후 승인을 받는다. `## 남은 contract`에는 각 plan이 넘긴 `남은 contract` 항목의 링크만 모으고, 그 contract가 처리되거나 조건이 바뀔 때만 갱신한다.
6. **계약 전환 지점의 경계 점검.** Phase 인계나 핵심 계약 전환(새 영속 형식·트랜잭션 모델 도입 등) 지점에서, 그동안 바뀐 경계만 구조 기준(`ARCHITECTURE.md`·done 구조 plan)과 대조해 새 책임·새 소유자·새 의존·검사 범위 공백을 보고한다. 구조를 바꿔야 하면 기존 모듈 점검(구조 plan)으로 올리고 이 자리에서 리팩터링하지 않는다. plan 개수 주기로 전체를 점검하지 않는다 — 개수는 구조 위험과 상관이 없다.

## 영향 범위
## 잠재 에러
## 범위
