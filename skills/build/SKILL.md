# jay-flow: build

핵심 원리: **오라클이 완료 기준이다.** "다 됐다"는 자기보고는 증거가 아니고, test/type/build 실행 출력이 증거다. 그리고 에이전트는 plan에서 표류하므로 task마다 plan을 다시 읽는다(plan 재주입).

## 절차

1. **plan 찾기.** 대화에서 지정된 것 우선, 없으면 `.plans/`의 최신 `in-progress`. **유효본은 `.plans/<slug>/`의 최고 버전(vN) 파일** — 이전 버전은 읽기 전용 이력이다. 승인된 plan이 없으면 build를 시작하지 말고 plan부터(자유 구현 금지).

2. **오라클 탐지.** repo에서 test/type/build 명령을 찾는다(`package.json` scripts / `Makefile` / `pubspec.yaml` / `pyproject` 등). 없으면 "오라클 미배선 — 검증 안 된 코드가 된다"를 맨 앞에 경고하고 사용자 확인 후에만 진행. 가능하면 특성 테스트부터 배선.

3. **task 분류.** plan의 task를 셋으로 나눈다(plan의 `파일:` 필드가 판정 근거):
   - **공유분**: 다른 task가 기대는 것(타입·스키마·계약·공유 유틸) — 먼저, 순차로.
   - **독립분**: 담당 파일이 서로 겹치지 않는 task — **병렬 fan-out이 기본**.
   - **겹침분**: 파일이 겹치거나 의존이 있는 task — 순차.
   ⚠️ 파일 목록만 믿지 마라 — layer를 가로지르는 task는 공유 타입·계약을 거친다. 겹침이 의심되면 순차로(false-independence가 병렬의 최대 실패모드다).

4. **task 실행 — 구현은 전부 `jay-flow:builder`(sonnet). 메인은 구현하지 않는다.**
   - **공유분·겹침분(순차)**: builder를 한 번에 하나씩, 순서대로 호출.
   - **독립분(병렬)**: builder를 **한 메시지에서 동시 호출**.
   - 어느 쪽이든 각 builder에 넘긴다: plan slice + 오라클 명령 + 담당 파일 목록. builder는 green까지 repair(캡 3회)하고 실제 오라클 출력·변경 파일을 반환한다.
   - **메인이 직접 구현하는 예외는 둘뿐**: ① 자명한 몇 줄짜리 task(디스패치 오버헤드가 이득을 넘는다) ② **에스컬레이션** — builder가 캡 소진 후에도 미green이면 그 task는 메인이 직접 잡는다(세션 모델이 상위이므로 이것이 모델 에스컬레이션이다; builder의 실패 출력 요약만 참고, 깨진 코드에 앵커링 금지). 메인도 캡 3회 초과면 멈추고 실패 출력과 함께 사용자에게.
   - **판정은 메인이 한다** (task 완료마다):
     - **drift check**: diff가 slice와 일치하나 — 초과(안 시킨 것 추가) / 누락 / 다르게 함. builder 자기보고가 아니라 diff로 판정. **공유분은 특히 엄격히** — 계약(타입·스키마) 오류는 컴파일이 통과해도 하위 task 전부로 전파된다. 구현 쪽 문제면 고치게 하고, **plan이 틀린 거면 멈추고 사용자에게** — 수정 합의 시 **새 버전 파일**(vN+1, `변경:` 한 줄 + task 상태 이월)로 저장 후 그 버전 기준으로 계속(기존 파일 편집 금지 — plan 스킬의 버전 규칙).
     - **고위험 표면 확인**: auth·권한·schema/persistence·public API·billing·concurrency·외부 I/O를 건드렸으면 변경 라인이 테스트에 닿는지 확인. 안 닿으면 해당 라인을 명시해 보고("low-risk"로 뭉개고 자가 통과 금지).
   - 체크박스 갱신 — **최신 버전 파일에 in-place**(실행 상태는 버전 사유가 아니다).

5. **마무리.** 전체 오라클 1회 실행(병렬 결과 통합 후 필수 — task별 green ≠ 전체 green) → 요약 보고: 무엇을 구현 / 오라클 결과(실제 출력 근거) / plan 이탈 여부 / 미해결. 이어서 review로.

## 원칙

- **모델 배치**: 판정·오케스트레이션(plan 해석, drift 판정)은 메인 = 상위 모델, 구현은 builder = sonnet — **순차든 병렬이든**. 이유 둘: 단가(구현이 토큰 물량의 대부분), 컨텍스트 위생(메인이 구현 잔해로 차면 판정 품질이 떨어진다). 판정 슬롯이 구현 슬롯보다 약해지면 안 된다 — drift check는 builder에게 시키지 않는다.
- 오라클 red를 숨기지 않는다 — red면 red라고, 출력과 함께.
