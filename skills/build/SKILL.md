# jay-flow: build

핵심 원리: **오라클이 완료 기준이다.** "다 됐다"는 자기보고는 증거가 아니고, test/type/build 실행 출력이 증거다. 그리고 에이전트는 plan에서 표류하므로 task마다 plan을 다시 읽는다(plan 재주입).

## 절차

1. **plan 찾기.** 대화에서 지정된 것 우선, 없으면 `.plans/`의 최신 `in-progress`. **유효본은 `.plans/<slug>/`의 최고 버전(vN) 파일** — 이전 버전은 읽기 전용 이력이다. 승인된 plan이 없으면 build를 시작하지 말고 plan부터(자유 구현 금지).

2. **베이스 확인 + 오라클 탐지.**
   - **신선도 게이트는 hook이 강제한다.** 이 스킬 호출 직전에 플러그인 hook(`scripts/freshness-gate.sh`)이 `git fetch` 후 로컬 HEAD가 upstream보다 뒤면 호출 자체를 차단하고 뒤처진 커밋 목록을 돌려준다 — 여기까지 왔으면 통과한 것이다(원격이 없으면 hook은 통과시킨다). 차단 메시지를 받았으면 build를 시작하지 말고 사용자에게 그 목록과 함께 알린다. 이유 둘: ① plan의 영향 범위는 실측(Grep)으로 잡는데, stale 트리 위에서 잰 실측은 틀린 전제다 ② 체크포인트 커밋과 drift 기준선이 전부 build 시작 시점 HEAD에 기댄다. 오라클이 못 잡는 부류다 — stale 베이스 위에서도 전부 green일 수 있다.
   - **오라클 탐지.** repo에서 test/type/build 명령을 찾는다(`package.json` scripts / `Makefile` / `pubspec.yaml` / `pyproject` 등). 없으면 "오라클 미배선 — 검증 안 된 코드가 된다"를 맨 앞에 경고하고 사용자 확인 후에만 진행. 가능하면 특성 테스트부터 배선.

3. **task 분류.** plan의 task를 넷으로 나눈다(판정 근거는 plan의 `파일:` 필드 + **구조 다이어그램** — 다이어그램의 공유 노드 = 공유분, 레이어 경계를 가로지르는 흐름 = 겹침 의심):
   - **공유분**: 다른 task가 기대는 것(타입·스키마·계약·공유 유틸) — 먼저, 순차로.
   - **독립분**: 담당 파일이 서로 겹치지 않는 task — **병렬 fan-out이 기본**.
   - **겹침분**: 파일이 겹치거나 의존이 있는 task — 순차.
   - **wide refactor**: plan이 expand → migrate → contract로 쪼개 놓은 것 — **순서는 고정**이다. expand가 green이 되기 전엔 migrate를 시작하지 않고, contract는 전 배치가 끝난 뒤에만. migrate 배치끼리는 담당 파일이 겹치지 않으면 **독립분으로 병렬 가능**하다(구 형태가 살아 있으므로 배치 단독으로도 green이 난다). plan이 "마지막 통합 task에서만 green"이라고 적었으면 그 배치들은 순차로 강등한다.
   ⚠️ 파일 목록만 믿지 마라 — layer를 가로지르는 task는 공유 타입·계약을 거친다. 겹침이 의심되면 순차로(false-independence가 병렬의 최대 실패모드다).

4. **task 실행 — 구현은 전부 `jay-flow:builder`(세션 모델, low effort). 메인은 구현하지 않는다.**
   - **공유분·겹침분(순차)**: builder를 한 번에 하나씩, 순서대로 호출 — **전체 오라클 명령**을 넘긴다.
   - **독립분(병렬)**: builder를 **한 메시지에서 동시 호출** — **task-scoped 오라클만** 넘긴다(plan의 `완료:` 기준에 해당하는 테스트·타입체크). 같은 working tree에서 전체 스위트를 동시에 돌리면 빌드 캐시·lock 파일·데몬·포트에서 충돌한다. 전체 스위트는 마무리(6)에서 메인이 1회 — 검증 손실 없음. **task-scoped 오라클이 아예 없으면**(`완료:` 기준에 돌릴 명령이 없으면) 타입체크라도 넘기고, 그마저 없으면 그 task는 **순차로 강등** — 검증 수단 없는 병렬 주행 금지.
   - 어느 쪽이든 각 builder에 넘긴다: plan slice + 오라클 명령(위 구분대로) + 담당 파일 목록 + **구조 축의 `구조 관례:` 줄**(slice에 §구조가 안 들어가는 task라도 이 줄은 항상 같이 넘긴다 — builder는 slice만 보므로 **새 파일에는 따라 할 주변 코드가 없고**, 그때 관례의 유일한 출처가 이 줄이다). builder는 green까지 repair(캡 3회)하고 실제 오라클 출력·변경 파일을 반환한다.
   - **메인이 직접 구현하는 예외는 셋뿐**: ① 자명한 몇 줄짜리 task(디스패치 오버헤드가 이득을 넘는다) ② 단순화 pass(5 — 판정 성격이 강하고 diff가 작다) ③ **에스컬레이션** — builder가 캡 소진 후에도 미green이면 그 task는 메인이 직접 잡는다(builder는 low effort, 메인은 기본 effort이므로 이것이 effort 에스컬레이션이다). 잡기 전에 **해당 task의 변경을 직전 체크포인트로 되돌리고 처음부터** — builder의 실패 출력 요약만 참고, 깨진 코드는 트리에서도 컨텍스트에서도 치운다(앵커링 금지). 메인도 캡 3회 초과면 멈추고 실패 출력과 함께 사용자에게.
   - **판정은 메인이 한다** (task 완료마다):
     - **drift check**: diff가 slice와 일치하나 — 초과(안 시킨 것 추가) / 누락 / 다르게 함. builder 자기보고가 아니라 diff로 판정 — **기준선은 직전 체크포인트 커밋**(첫 task는 build 시작 시점 HEAD), 병렬분은 builder가 반환한 담당 파일 목록으로 diff 범위를 자른다. **공유분은 특히 엄격히** — 계약(타입·스키마) 오류는 컴파일이 통과해도 하위 task 전부로 전파된다. 구현 쪽 문제면 고치게 하고, **plan이 틀린 거면 멈추고 사용자에게** — 수정 합의 시 **새 버전 파일**(vN+1, `변경:` 한 줄 + task 상태 이월)로 저장 후 그 버전 기준으로 계속(기존 파일 편집 금지 — plan 스킬의 버전 규칙).
     - **고위험 표면 확인**: auth·권한·schema/persistence·public API·billing·concurrency·외부 I/O를 건드렸으면 변경 라인이 테스트에 닿는지 확인. **판정은 세 값이다** — `닿음` / **`닿지만 seam이 얕음`** / `안 닿음`. 닿기만 하면 통과가 아니다: 그 테스트가 **실제 위험 패턴을 호출 지점 형태 그대로** 태우는지 본다(호출자 여럿이 얽혀야 나는 문제를 단일 호출자 단위테스트로 덮는 식이면 도달했어도 거짓 확신이다). **올바른 seam이 없다는 것 자체가 발견이다** — 얕은 seam에 테스트를 얹어 통과시키지 말고 그 사실을 보고해라. `안 닿음`이든 `얕음`이든 해당 라인을 명시해 보고("low-risk"로 뭉개고 자가 통과 금지).
   - **교정은 새 builder를 재-dispatch한다** — 담당 파일과 무엇이 어긋났는지를 slice와 함께 넘긴다. 교정이 끝나고 **다시 판정한 뒤에** 체크포인트 커밋을 찍는다(교정 미완 상태의 커밋은 기준선을 오염시킨다).
   - **체크포인트 커밋** — 오라클 green + 판정 통과한 task마다 커밋한다(`task N: <무엇>` 한 줄, **담당 파일만 add** — 사용자의 무관한 변경을 쓸어 담지 않는다). drift 판정 기준선·단순화 되돌리기·에스컬레이션 초기화가 전부 이 커밋에 기댄다. 이력 정리(squash)는 사용자 몫 — 임의로 하지 않는다.
   - 체크박스 갱신 — **최신 버전 파일에 in-place**(실행 상태는 버전 사유가 아니다).

5. **단순화 pass (전체 green 후, review 전 — 메인이 한다).** 통합 오라클을 돌려 green이면 consolidated diff를 훑어 **우발적 복잡도만** 수정한다(red면 6의 통합 red 절차부터 — 단순화는 green 위에서만) — 줄일 수 있는데 안 줄인 것: 불필요한 추상, 중복, 과잉 방어, 죽은 분기, 장황한 구현.
   - **동작·계약 불변이 조건.** 공개 시그니처·스키마·직렬화 포맷을 바꾸는 단순화는 여기서 금지 — 그건 plan 수정(새 버전) 사안이다. "단순화"가 이탈의 면죄부가 되면 안 된다.
   - 수정 후 **전체 오라클 재실행** — red면 직전 체크포인트로 되돌린다(단순화 전 상태가 커밋돼 있으므로 기계적). green이면 단순화도 체크포인트 커밋.
   - **없으면 없다고 넘어간다** — 억지 리팩토링 금지.

6. **마무리.** 전체 오라클 1회 실행(병렬 결과 통합 후 필수 — task별 green ≠ 전체 green이고, **병렬 task는 task-scoped 검증만 거쳤으므로 여기가 전체 스위트의 유일한 게이트다**; 단순화 pass에서 이미 돌렸으면 그 결과로 갈음).
   - **통합 red면** (이 설계의 예상된 실패 지점 — 곧바로 사용자에게 던지지 않는다): 실패 출력·diff로 **책임 task를 귀속** → 그 task 범위로 builder repair 1라운드 — 이 시점엔 병렬 형제가 없으므로 **전체 오라클 명령**을 넘긴다 → 여전히 red면 메인 에스컬레이션(4의 사다리 그대로: 체크포인트로 되돌리고 처음부터) → 그래도 red면 실패 출력과 함께 사용자에게. 특정 task로 귀속되지 않는 red(진짜 통합 상호작용)는 처음부터 메인이 잡는다.
   - green이면 요약 보고: 무엇을 구현 / 오라클 결과(실제 출력 근거) / plan 이탈 여부 / 단순화 적용 내역 / 체크포인트 커밋 목록 / 미해결. **정지 조건(미green·plan 오류·고위험 미도달 보고)에 걸리지 않았다면 사용자 입력을 기다리지 말고 곧바로 Skill 도구를 `jay-flow:review`로 호출한다**(산문으로 "review를 이어서 실행한다"고 적지 말고 도구 이름을 짚어라 — 지시가 서술로 읽히면 연속 주행이 끊긴다) — 사람 게이트는 plan 승인(앞)과 review 판정(뒤) 둘뿐이다.

## 원칙

- **모델 배치**: 판정·오케스트레이션(plan 해석, drift 판정)은 메인 = 기본 effort, 구현은 builder = 같은 모델의 low effort — **순차든 병렬이든**. 이유는 컨텍스트 위생이다(메인이 구현 잔해로 차면 판정 품질이 떨어진다). 단가는 이유가 아니다 — 측정상 sonnet builder와 task당 비용이 같았다(`evals/build-ledger`). 판정 슬롯이 구현 슬롯보다 약해지면 안 된다 — drift check는 builder에게 시키지 않는다.
- **에이전트 팀 기능은 쓰지 않는다** — 서브에이전트에 `name`을 붙이지 말고, 완료된 builder를 재개하지 마라. 재개가 아끼는 건 재독 비용뿐인데, 이름 붙은 에이전트는 팀 로스터에 영구 등재돼 build 한 번에 로스터가 수십 줄로 불어나고, 가용성이 환경(팀 모드 on/off)에 좌우된다. 절차가 환경에 의존하면 안 된다. 교정은 재-dispatch로 한다.
- 오라클 red를 숨기지 않는다 — red면 red라고, 출력과 함께.
