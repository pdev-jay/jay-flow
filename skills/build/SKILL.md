# jay-flow: build

핵심 원리: **오라클이 완료 기준이다.** "다 됐다"는 자기보고는 증거가 아니고, test/type/build 실행 출력이 증거다. 그리고 에이전트는 plan에서 표류하므로 task마다 plan을 다시 읽는다(plan 재주입).

## FAST 루트 (plan 없이 가는 경우)

**승인된 plan이 없을 때만** 판정한다. **다섯이 전부 참일 때만 FAST**고, 하나라도 거짓이거나 판단이 안 서면 plan으로 간다 — 기본값은 plan이다.

1. **고위험 표면을 안 건드린다** — auth·권한·schema/persistence·public API·billing·concurrency·외부 I/O.
2. **가역적이다** — 되돌리기가 `git revert` 하나로 끝난다. 마이그레이션·배포·외부 상태 변경 없음.
3. **오라클이 변경 라인에 닿는다** — 지금 돌릴 수 있는 test/type/build가 이미 있다. **오라클 미배선이면 FAST 금지** — 검증 수단이 없는 상태에서 게이트를 하나 빼는 것이다.
4. **(수정류) 원인이 이미 확정돼 있다** — 사슬을 팔 것이 없는 부류(오타·상수·명백한 off-by-one·빠진 null 체크). 증상만 알고 원인을 모르면 plan의 증거 라벨 절차로 간다.
5. **한 seam 안이다** — 새 경계·새 모듈이 없고 레이어를 가로지르지 않는다.

판정 기준은 **파일 수나 줄 수가 아니라 위험 표면**이다 — 한 줄이어도 1을 건드리면 plan이고, 파일 여럿이어도 다섯을 다 만족하면 FAST다.

**사용자가 plan을 명시적으로 요청했으면 이 판정을 하지 않는다**("plan 세우자 / 계획부터 / 어떻게 할지 정리해줘"). 판정 대상은 plan을 안 거치고 들어온 작아 보이는 변경이지, 사용자가 계획을 달라고 한 건이 아니다. **진단·리뷰·분석만 요청받았으면 이 스킬 자체가 아니다** — 그 요청은 수정을 승인하지 않는다.

**진행 중인 plan이 있으면 FAST로 우회하지 않는다.** `.plans/`에 `in-progress`·`on-hold` plan이 있고 이 변경이 그 plan의 담당 파일이나 task와 겹치면 FAST 판정 대상이 아니다 — 그 plan을 이어가거나(build) 새 버전으로 반영한다. plan 밖에서 같은 파일을 고치면 그 plan의 drift 기준선과 체크박스가 실제 트리와 어긋난다.

**절차**: (수정류면) **고치기 전에 증상을 오라클로 먼저 재현**한다 — red를 본 뒤 수정해야 green이 수정의 증거가 된다(재현이 안 되면 4번 조건이 거짓일 가능성이 크다 — plan으로) → 메인이 직접 수정 → **오라클 1회** → diff를 직접 다시 읽어 놓친 호출부·경계값·의도 밖 변경을 확인 → **diff를 사용자에게 보고하고 멈춘다**(예상 밖의 durable 증거가 드러났으면 review 6단계 학습 제안을 붙인다). 수정 후 오라클이 red여서 **고친 구현을 다시 고쳤다면**, 첫 시도가 틀렸다는 뜻이고 자기가 고친 코드를 자기 합리화 위에서 보게 된다 — 보고 전에 `jay-flow:reviewer`를 한 번 거친다(plan 없음 — 요청 원문·working tree diff·오라클 출력을 넘기고, 전후 트리 지문 확인은 review 3단계와 같다). plan 파일·체크포인트 커밋·builder 디스패치·`jay-flow:review`는 전부 없다(위 재수정 시 reviewer 1회만 예외). 빼는 것은 사람 게이트 둘 중 **앞쪽(plan 승인)뿐**이고 뒤쪽(사용자가 diff를 읽는 것)은 그대로다 — diff 자체가 계획인 크기라 승인 왕복을 안 붙이는 것이지 확인을 빼는 게 아니다.

**이탈 조건.** 착수 후 다섯 중 하나라도 거짓으로 드러나면 **그 자리에서 멈추고 변경을 되돌린 뒤 plan으로 올린다.** "거의 다 했으니 마저 한다"는 없다 — FAST가 품질 구멍이 되는 경로가 정확히 이것이다. 되돌린 사실과 무엇이 드러났는지를 사용자에게 알린다.

## 절차

1. **plan 찾기.** 대화에서 지정된 것 우선, 없으면 `.plans/`의 최신 `in-progress`(`on-hold`는 건너뛴다 — 대기 중인 구조 plan이 먼저다). **유효본은 `.plans/<slug>/`의 최고 버전(vN) 파일** — 이전 버전은 읽기 전용 이력이다. **승인된 plan이 없으면 아래 FAST 판정을 먼저 한다** — 통과면 FAST 루트로, 아니면 plan부터(그 사이는 없다. 판정 없는 자유 구현 금지).

2. **베이스 확인 + 오라클 탐지.**
   - **신선도 게이트는 hook이 강제한다.** 이 스킬 호출 직전에 플러그인 hook(`scripts/freshness-gate.sh`)이 `git fetch` 후 로컬 HEAD가 upstream보다 뒤면 호출 자체를 차단하고 뒤처진 커밋 목록을 돌려준다 — 여기까지 왔으면 통과한 것이다(원격이 없으면 hook은 통과시킨다). 차단 메시지를 받았으면 build를 시작하지 말고 사용자에게 그 목록과 함께 알린다. 이유 둘: ① plan의 영향 범위는 실측(Grep)으로 잡는데, stale 트리 위에서 잰 실측은 틀린 전제다 ② 체크포인트 커밋과 drift 기준선이 전부 build 시작 시점 HEAD에 기댄다. 오라클이 못 잡는 부류다 — stale 베이스 위에서도 전부 green일 수 있다.
   - **기존 미커밋 변경 확인.** `git status --porcelain`으로 사용자의 미커밋 변경을 본다. plan의 담당 파일과 **겹치는 변경**이 있으면 시작 전에 사용자에게 묻는다(먼저 커밋 / stash / 이 build에 포함) — 겹친 채로 가면 체크포인트 커밋이 사용자 변경을 쓸어 담고, 에스컬레이션 되돌리기가 그것을 지운다. 겹치지 않는 변경은 그대로 두고 add하지 않는다. 대신 **시작 시점의 `git status --porcelain` 목록과 그 파일들의 내용 해시를 기준선으로 적어 둔다** — 아래 배치 종료 확인과 review는 이 기준선과 다른 것만 build의 변경으로 본다.
   - **오라클 탐지.** repo에서 test/type/build 명령을 찾는다(`package.json` scripts / `Makefile` / `pubspec.yaml` / `pyproject` 등). 없으면 "오라클 미배선 — 검증 안 된 코드가 된다"를 맨 앞에 경고하고 사용자 확인 후에만 진행. 가능하면 특성 테스트부터 배선.

3. **task 분류.** plan의 task를 넷으로 나눈다(판정 근거는 plan의 `파일:` 필드 + **구조 다이어그램** — 다이어그램의 공유 노드 = 공유분, 레이어 경계를 가로지르는 흐름 = 겹침 의심):
   - **공유분**: 다른 task가 기대는 것(타입·스키마·계약·공유 유틸) — 먼저, 순차로.
   - **독립분**: 담당 파일이 서로 겹치지 않고, 서로의 산출 계약을 소비하지 않고, **task-scoped 오라클이 공유 자원을 쓰지 않는** task — **병렬 fan-out이 기본**. 공유 자원 = 빌드 캐시·lock·데몬·포트·에뮬레이터·실기기·변경 가능한 fixture/DB. 파일이 disjoint여도 오라클이 같은 에뮬레이터나 같은 테스트 DB를 쓰면 서로의 green/red를 오염시킨다 — 순차.
   - **겹침분**: 파일이 겹치거나 의존이 있는 task — 순차.
   - **wide refactor**: plan이 expand → migrate → contract로 쪼개 놓은 것 — **순서는 고정**이다. expand가 green이 되기 전엔 migrate를 시작하지 않고, contract는 전 배치가 끝난 뒤에만. migrate 배치끼리는 담당 파일이 겹치지 않으면 **독립분으로 병렬 가능**하다(구 형태가 살아 있으므로 배치 단독으로도 green이 난다). plan이 단독 green이 안 되는 배치를 한 task로 묶었으면 그 task는 builder 하나가 맡고 green도 그 task 끝에서 한 번이다. 묶지 않고 "중간 red, 마지막 통합 task에서만 green"으로 적힌 plan이면 진행하지 말고 plan 오류로 멈춘다 — 중간 task는 green 요구에 걸려 끝까지 갈 수 없다(새 버전에서 한 task로 묶는다).
   ⚠️ 파일 목록만 믿지 마라 — layer를 가로지르는 task는 공유 타입·계약을 거친다. 겹침이 의심되면 순차로(false-independence가 병렬의 최대 실패모드다).

4. **task 실행 — 구현은 전부 `jay-flow:builder`(세션 모델, low effort). 메인은 구현하지 않는다.**
   - **공유분·겹침분(순차)**: builder를 한 번에 하나씩, 순서대로 호출 — **전체 오라클 명령**을 넘긴다.
   - **독립분(병렬)**: builder를 **한 메시지에서 동시 호출** — **task-scoped 오라클만** 넘긴다(plan의 `완료:` 기준에 해당하는 테스트·타입체크). 같은 working tree에서 전체 스위트를 동시에 돌리면 빌드 캐시·lock 파일·데몬·포트에서 충돌한다. 전체 스위트는 마무리(6)에서 메인이 1회 — 검증 손실 없음. **task-scoped 오라클이 아예 없으면**(`완료:` 기준에 돌릴 명령이 없으면) 타입체크라도 넘기고, 그마저 없으면 그 task는 **순차로 강등** — 검증 수단 없는 병렬 주행 금지.
   - 어느 쪽이든 각 builder에 넘긴다: plan slice + 오라클 명령(위 구분대로) + 담당 파일 목록(`## 소유 보정` 포함) + **구조 축의 `구조 관례:` 줄**(slice에 §구조가 안 들어가는 task라도 이 줄은 항상 같이 넘긴다 — builder는 slice만 보므로 **새 파일에는 따라 할 주변 코드가 없고**, 그때 관례의 유일한 출처가 이 줄이다). plan `구조 기준:`에 `범용`이 들어가면 **범용 규칙 문서의 절대 경로**(`${CLAUDE_PLUGIN_ROOT}/reference/structure-rules.md`)와 그 줄이 인용한 규칙 번호·범위도 넘긴다 — builder 지시에는 플러그인 경로가 없으므로 메인이 준다. `범용`이 없으면 넘기지 않는다(기존 관례를 따르는 task에 범용 규칙을 주면 둘이 충돌한다). roadmap 위임 중이면 roadmap `## 학습`에서 **이 task에 관련된 항목만** 넘긴다(테스트 환경 초기화 관례처럼 이미 풀린 문제를 builder가 다시 풀지 않게 — 실측: 한 안건에서 해결한 DOM 테스트 초기화를 다음 안건의 builder가 다시 디버깅했다). builder는 green까지 repair(캡 3회)하고 실제 오라클 출력·변경 파일을 반환한다.
   - **roadmap에 종료 시각이 있으면 task마다 dispatch 직전에** 남은 시간이 이 task의 구현·검증·교정과 안전 정리를 담는지 본다 — 부족하면 새 task를 시작하지 않고 마지막 체크포인트 상태를 인계한다(plan 하나가 여러 task면 plan 경계만 보면 종료 시각 뒤에 task가 열린다).
   - **builder가 돌아가는 동안 메인은 다음 task·다음 plan을 읽기 전용으로 조사할 수 있다** — 사용처 열거·fixture 확인·plan 초안. 트리 쓰기와 오라클 실행은 하지 않는다(builder의 green을 오염시킨다). 조사 결과는 builder 결과를 판정한 뒤 착수 직전에 최신 계약과 다시 대조한다.
   - **메인이 직접 구현하는 예외는 셋뿐**: ① 자명한 몇 줄짜리 task(디스패치 오버헤드가 이득을 넘는다) ② 단순화 pass(5 — 판정 성격이 강하고 diff가 작다) ③ **에스컬레이션** — builder가 캡 소진 후에도 미green이면 그 task는 메인이 직접 잡는다(builder는 low effort, 메인은 기본 effort이므로 이것이 effort 에스컬레이션이다). 잡기 전에 **그 builder와 그것이 띄운 오라클 프로세스가 끝났는지 확인하고**(살아 있는 쓰기 주체 위에서 되돌리면 되돌린 트리가 다시 오염된다) **해당 task의 변경을 직전 체크포인트로 되돌리고 처음부터** — builder의 실패 출력 요약만 참고, 깨진 코드는 트리에서도 컨텍스트에서도 치운다(앵커링 금지). 메인도 캡 3회 초과면 멈추고 실패 출력과 함께 사용자에게 — 서로 다른 시도가 원인 미확정인 채 실패했다면 plan의 모델·effort 추천 규칙대로 한 단계 위를 한 줄로 권한다.
   - **판정은 메인이 한다** (task 완료마다):
     - **drift check**: diff가 slice와 일치하나 — 초과(안 시킨 것 추가) / 누락 / 다르게 함. builder 자기보고가 아니라 diff로 판정 — **기준선은 직전 체크포인트 커밋**(첫 task는 build 시작 시점 HEAD), 병렬분은 builder가 반환한 담당 파일 목록으로 diff 범위를 자르되, **배치가 끝나면 실제 변경 파일(`git status --porcelain`에서 시작 기준선과 목록·해시가 같은 항목을 뺀 것)이 배치 담당 파일(소유 보정 포함)의 합집합 안인지 확인한다** — 밖의 파일이 바뀌었으면 자기보고에 없는 수정이고 drift다. 기준선의 사용자 변경은 drift가 아니다. **공유분은 특히 엄격히** — 계약(타입·스키마) 오류는 컴파일이 통과해도 하위 task 전부로 전파된다. 구현 쪽 문제면 고치게 하고, 담당 파일 누락이면 아래 소유 보정 절차로 먼저 분류한다. **plan이 틀린 거면 멈추고 사용자에게**(roadmap에 사용자의 plan 승인 위임 원문이 기록돼 있으면 그 범위 안의 계약 수정은 메인이 새 버전으로 승인하고 진행한다 — 위임 밖의 결정이 필요하면 정지) — 틀린 이유가 **기존 구조 변경이 필요해서**면 plan 스킬의 "feature 중 드러난 기존 구조 변경" 절차대로 **두 선택지(새 버전에 공유분 task로 추가 / 구조 plan 분리)를 흐름 비교와 함께 제시**하고 사용자가 고르게 한다(분리를 고르면 체크포인트 커밋은 그대로 두고 feature plan은 `on-hold`). 그 외 이유거나 새 버전을 고르면 수정 합의 시 **새 버전 파일**(vN+1, `변경:` 한 줄 + task 상태 이월)로 저장 후 그 버전 기준으로 계속(기존 파일 편집 금지 — plan 스킬의 버전 규칙).
     - **고위험 표면 확인**: auth·권한·schema/persistence·public API·billing·concurrency·외부 I/O를 건드렸으면 변경 라인이 테스트에 닿는지 확인. **판정은 세 값이다** — `닿음` / **`닿지만 seam이 얕음`** / `안 닿음`. 닿기만 하면 통과가 아니다: 그 테스트가 **실제 위험 패턴을 호출 지점 형태 그대로** 태우는지 본다(호출자 여럿이 얽혀야 나는 문제를 단일 호출자 단위테스트로 덮는 식이면 도달했어도 거짓 확신이다). **올바른 seam이 없다는 것 자체가 발견이다** — 얕은 seam에 테스트를 얹어 통과시키지 말고 그 사실을 보고해라. `안 닿음`이든 `얕음`이든 해당 라인을 명시해 보고("low-risk"로 뭉개고 자가 통과 금지).
     - **구조 규칙 확인**: plan `## 구조`에 `구조 규칙:`이 있으면 그 검색 명령들을 다시 돌린다. 위반이 plan 시점보다 늘었으면 **drift다** — 오라클이 green이어도 통과가 아니다(적합도 함수가 아직 안 선 구간에선 이게 유일한 확인이다). 적합도 함수 task는 **위반 주입 → red → 되돌림**을 실제로 했는지 출력으로 확인한다. `구조 기준:`에 `범용`이 들어가면 diff가 범용이 맡은 범위 안에서 새로 만든 §14 표의 항목(Domain·입출력 계약·Controller·사용권·Coordinator·공개 사실 스트림·Feature·영역 묶음)마다 plan에 §14 근거 한 줄이 있는지 본다 — 없으면 drift다(R17). `상태·실행 모델:`이 있으면 diff가 같은 상태를 다른 컴포넌트에 새로 들거나, 명시한 실행 컨텍스트 밖에서 상태를 만지거나, 시작한 것을 정리하지 않는 경로를 만들었는지 본다 — 그러면 drift.
   - **교정은 새 builder를 재-dispatch한다** — 담당 파일과 무엇이 어긋났는지를 slice와 함께 넘긴다. 교정이 끝나고 **다시 판정한 뒤에** 체크포인트 커밋을 찍는다(교정 미완 상태의 커밋은 기준선을 오염시킨다).
   - **repair 캡은 builder가 아니라 원인 계보에 붙는다.** 같은 원인을 고치러 새 builder를 띄울 때는 남은 횟수와 앞선 시도의 가설 한 줄씩을 넘긴다 — 새 dispatch나 소유 보정으로 캡을 초기화하지 않는다(초기화하면 캡이 에스컬레이션을 막지 못하고 같은 가설이 반복된다). 실패 출력이 앞선 것과 **다른 원인**을 보이면 새 계보이고, 메인이 그 근거를 한 줄로 적는다. 새 계보의 최초 dispatch만 3회로 시작한다. 이 캡은 builder 단계의 것이고, 소진 후 메인 에스컬레이션은 별도 단계로 최대 3회다.
   - **builder가 담당 밖 수정이 필요하다고 멈추면** 메인이 판정한다: ① 기존 AC를 구현하는 caller·테스트·fixture 누락인가 ② 병렬 형제의 담당 파일과 겹치지 않나 ③ 기준선의 사용자 미커밋 변경과 겹치지 않나. 셋 다 맞으면 plan 최신 버전의 `## 소유 보정`에 append하고(새 버전 아님) 확장된 담당 목록으로 builder를 재-dispatch한다(캡 승계). 새 동작·공개 계약·schema·권한 의미가 따라 들어오면 소유 보정이 아니다 — drift의 plan 오류 경로로 간다. drift 판정의 담당 범위는 담당 파일 ∪ 소유 보정이다.
   - **체크포인트 커밋** — 오라클 green + 판정 통과한 task마다 커밋한다(메시지는 repo·사용자의 커밋 규칙을 따르고 task 번호를 담는다 — 규칙이 없으면 `task N: <무엇>` 한 줄. **담당 파일만 add** — 사용자의 무관한 변경을 쓸어 담지 않는다). **사용자가 승인한 plan을 build하는 것 자체가 체크포인트 커밋에 대한 명시 승인이다**(사용자 결정 — 승인 없는 FAST·자동 선택된 build는 해당 없음) — "커밋은 명시 지시 때만" 류 전역 규칙과 충돌하지 않는다. 승인 범위는 이 체크포인트 커밋까지고 push·squash·amend는 아니다. FAST 루트는 커밋하지 않는다. drift 판정 기준선·단순화 되돌리기·에스컬레이션 초기화가 전부 이 커밋에 기댄다. 이력 정리(squash)는 사용자 몫 — 임의로 하지 않는다.
   - 체크박스 갱신 — **최신 버전 파일에 in-place**(실행 상태는 버전 사유가 아니다).

5. **단순화 pass (전체 green 후, review 전 — 메인이 한다).** 유효한 전체 green을 확인하고(아래 원칙의 재사용 조건 — 없으면 실행) green이면 consolidated diff를 훑어 **우발적 복잡도만** 수정한다(red면 6의 통합 red 절차부터 — 단순화는 green 위에서만) — 줄일 수 있는데 안 줄인 것: 불필요한 추상, 중복, 과잉 방어, 죽은 분기, 장황한 구현.
   - **동작·계약 불변이 조건.** 공개 시그니처·스키마·직렬화 포맷을 바꾸는 단순화는 여기서 금지 — 그건 plan 수정(새 버전) 사안이다. "단순화"가 이탈의 면죄부가 되면 안 된다.
   - 수정 후 **전체 오라클 재실행** — red면 직전 체크포인트로 되돌린다(단순화 전 상태가 커밋돼 있으므로 기계적). green이면 단순화도 체크포인트 커밋.
   - **없으면 없다고 넘어간다** — 억지 리팩토링 금지.

6. **마무리.** 유효한 전체 green 확인, 없으면 전체 오라클 1회 실행(병렬 결과 통합 후엔 반드시 실행 — task별 green ≠ 전체 green이고, **병렬 task는 task-scoped 검증만 거쳤으므로 여기가 전체 스위트의 유일한 게이트다**; 단순화 pass에서 이미 돌렸으면 그 결과로 갈음). 출력은 builder와 같은 규칙으로 절삭한다 — quiet/실패 전용 옵션 + `tail`(종료 코드는 `pipefail`/`PIPESTATUS`로 오라클 자체의 것을 본다), red면 실패 블록만 인용. 전체 출력을 컨텍스트에 남기지 않는다.
   - **통합 red면** (이 설계의 예상된 실패 지점 — 곧바로 사용자에게 던지지 않는다): 실패 출력·diff로 **책임 task를 귀속** → 그 task 범위로 builder repair 1라운드 — 이 시점엔 병렬 형제가 없으므로 **전체 오라클 명령**을 넘긴다 → 여전히 red면 메인 에스컬레이션(4의 사다리 그대로: 체크포인트로 되돌리고 처음부터) → 그래도 red면 실패 출력과 함께 사용자에게. 특정 task로 귀속되지 않는 red(진짜 통합 상호작용)는 처음부터 메인이 잡는다.
   - **roadmap 위임 중이면** 이번 build에서 검증된 재사용 지식을 roadmap `## 학습`에 근거 위치와 함께 적는다. plan 종료·실제 총소요·재추정은 review accept 뒤에 기록한다(review·교정 시간이 빠진 완료 기록을 남기지 않는다).
   - green이면 요약 보고: 무엇을 구현 / 오라클 결과(실제 출력 근거) / plan 이탈 여부 / 단순화 적용 내역 / 체크포인트 커밋 목록 / 미해결. **정지 조건(미green·plan 오류·고위험 미도달 보고)에 걸리지 않았다면 사용자 입력을 기다리지 말고 곧바로 Skill 도구를 `jay-flow:review`로 호출한다**(산문으로 "review를 이어서 실행한다"고 적지 말고 도구 이름을 짚어라 — 지시가 서술로 읽히면 연속 주행이 끊긴다) — 사람 게이트는 plan 승인(앞)과 review 판정(뒤) 둘뿐이다.

## 원칙

- **모델 배치**: 판정·오케스트레이션(plan 해석, drift 판정)은 메인 = 기본 effort, 구현은 builder = 같은 모델의 low effort — **순차든 병렬이든**. 이유는 컨텍스트 위생이다(메인이 구현 잔해로 차면 판정 품질이 떨어진다). 단가는 이유가 아니다 — 측정상 sonnet builder와 task당 비용이 같았다(`evals/build-ledger`). 판정 슬롯이 구현 슬롯보다 약해지면 안 된다 — drift check는 builder에게 시키지 않는다.
- **에이전트 팀 기능은 쓰지 않는다** — 서브에이전트에 `name`을 붙이지 말고, 완료된 builder를 재개하지 마라. 재개가 아끼는 건 재독 비용뿐인데, 이름 붙은 에이전트는 팀 로스터에 영구 등재돼 build 한 번에 로스터가 수십 줄로 불어나고, 가용성이 환경(팀 모드 on/off)에 좌우된다. 절차가 환경에 의존하면 안 된다. 교정은 재-dispatch로 한다.
- **같은 입력의 전체 오라클은 다시 돌리지 않는다.** 전체 오라클은 쓰기를 멈춘 상태에서 돌리고, **실행 직전과 직후에 내용 지문** `t=$(mktemp -u) && GIT_INDEX_FILE=$t git add -A && GIT_INDEX_FILE=$t git write-tree; s=$?; rm -f $t; (exit $s)` 를 떠서 결과(실제 exit code·로그 위치)와 함께 둔다 — 임시 index에 ignore 밖의 working tree 전체를 담은 tree hash라 stage·커밋 여부와 무관하고(체크포인트 커밋으로 바뀌지 않는다) 삭제도 반영하며, 실제 index는 건드리지 않는다. ignored 의존성은 안 들어가므로 아래 의존성 조건이 따로 있다. 이후 단계(단순화 전·마무리·review 1단계)가 전체 오라클을 요구할 때 **전후 지문이 같았고, 지금 지문도 같고, 그 사이 활성 writer·의존성 설치·toolchain·오라클 명령 변경이 없었으면** 그 결과로 갈음한다. 하나라도 확인이 안 되거나 지문 계산이 실패하면 다시 돌린다 — 재사용의 실패 형태는 거짓 green이고, 그건 재실행 비용보다 비싸다. 병렬 task의 task-scoped green과 병렬 통합 전 결과는 재사용 대상이 아니다. 테스트만 바뀌어도 지문이 바뀐다 — 그게 의도다.
- 오라클 red를 숨기지 않는다 — red면 red라고, 출력과 함께.
