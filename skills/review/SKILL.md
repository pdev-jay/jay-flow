# jay-flow: review

핵심 원리: **오라클 먼저, 사람 판정.** 기계가 판정할 수 있는 것(test/type/build)을 먼저 다 짜내고, 그 위의 발견은 advisory로만 얹는다 — 게이트가 아니다.

## 절차

1. **전체 오라클.** test/type/build 실행. red면 리뷰가 아니라 수리가 먼저다 — build로 돌려보낸다.

2. **diff vs plan.** consolidated diff를 **최신 버전** plan과 대조:
   - 초과 구현(plan에 없는 것) / 누락(plan에 있는데 안 함) / 이탈(다르게 함) 목록.
   - 버전이 여러 개면 v1→vN의 `변경:` 이력을 먼저 훑는다 — diff가 plan과 달라도 **버전 이력에 있으면 승인된 변경, 없으면 이탈**이다.
   - plan의 **잠재 에러** 섹션에 적힌 시나리오가 실제로 처리됐는지 하나씩 확인 — 각 항목의 `검증:` 표기 기준으로(테스트라면 그 테스트가 실제 존재하고 도는지, `미검증`이면 지금도 미검증인지 명시).
   - plan **미해결·전제**에 `검증 필요`로 남은 항목이 build 중 해소됐는지 — 안 됐으면 advisory 최상단에 올린다.

3. **diff 자체 검토.** 변경된 코드만 본다. 잠재 에러 축(엣지·실패 경로·경계값) 중심 — plan 때 못 본 것 포함. 고위험 표면(auth·schema·billing·concurrency 등)의 변경 라인이 테스트에 닿는지 재확인.

4. **보고.** 발견을 심각도와 함께 나열 — advisory다, 머지 판정은 사용자. 근거 없는 발견은 만들지 않는다(없으면 없다고).

5. **done.** 사용자 accept 시 **최신 버전** plan 파일에 `status: done`. 남은 advisory 발견은 같은 파일 하단에 기록해 둔다(다음 작업의 씨앗).
