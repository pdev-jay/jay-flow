# jay-flow: review

핵심 원리: **오라클 먼저, 사람 판정.** 기계가 판정할 수 있는 것(test/type/build)을 먼저 다 짜내고, 그 위의 발견은 advisory로만 얹는다 — 게이트가 아니다.

## 절차

**단독 리뷰**(build 없이 "이 diff 리뷰해줘" — 대상 plan이 없거나 사용자가 범위를 지정): diff 범위는 사용자가 지정한 것, 2단계의 plan 대조는 대응되는 plan이 있을 때만, 3단계 reviewer에는 plan 대신 요청 원문을 넘긴다. **리뷰 요청은 수정을 승인하지 않는다** — 1단계 red여도 고치지 않고 보고한다. done 전이(5)는 plan이 있을 때만.


1. **전체 오라클.** test/type/build 실행. build가 남긴 전체 오라클 결과가 지금 트리와 같은 입력이면 그 결과로 갈음한다(재사용 조건은 build 원칙의 "같은 입력의 전체 오라클" 그대로 — 확인이 안 되면 실행). 갈음해도 실제 수집·skip과 고위험 호출 경계 도달은 그 출력에서 따로 본다. red면 리뷰가 아니라 수리가 먼저다 — build로 돌려보낸다.

2. **diff vs plan.** consolidated diff = **build 시작 시점 HEAD → 최신 체크포인트의 커밋 범위**(build 마무리 보고의 체크포인트 커밋 목록, 없으면 `git log`로 재구성 — build의 변경은 체크포인트 커밋에 들어가므로 `git diff` 단독은 build 변경을 보여 주지 않는다. working tree에 남은 변경은 build 시작 기준선의 사용자 변경이고 리뷰 대상이 아니다). 이를 **최신 버전** plan과 대조:
   - 초과 구현(plan에 없는 것) / 누락(plan에 있는데 안 함) / 이탈(다르게 함) 목록.
   - 버전이 여러 개면 v1→vN의 `변경:` 이력을 먼저 훑는다 — 대조 기준은 **최신 버전**이고, 이력은 최신 버전이 왜 v1과 다른지 설명할 뿐이다. diff가 v1과 달라도 최신 버전과 맞으면 승인된 변경이다. **이전 버전에만 있고 최신 버전에서 빠진 결정의 구현이 diff에 남아 있으면 이탈이다** — 폐기된 승인은 면책 사유가 아니다. `## 소유 보정`의 파일은 담당 범위로 본다.
   - plan의 **잠재 에러** 섹션에 적힌 시나리오가 실제로 처리됐는지 하나씩 확인 — 각 항목의 `검증:` 표기 기준으로(테스트라면 그 테스트가 존재하고 **1단계 오라클 출력에서 실제 수집·실행됐는지** — 전체 green은 그 테스트가 돌았다는 증명이 아니다, skip이면 미검증 취급. `미검증`이면 지금도 미검증인지 명시).
   - **원인·배경 라벨 확인**(수정류). `진단 + red`면 그 red 명령이 **1단계 오라클 출력에서 실제로 green이 됐는지** 본다 — 전체 green은 그 명령이 돌았다는 증명이 아니다. **`진단 + red 불가`면 대체 증거 재관측이 실제로 됐는지 묻는다** — 자동 오라클이 없어 여기가 유일한 확인 지점이고, 안 됐으면 "미검증"으로 advisory 최상단이다(build가 green이어도 원인이 사라졌다는 증거는 아직 없다). `원인 미상`이면 **원인 제거가 증명되지 않았다**는 사실을 보고에 그대로 싣는다.
   - plan `구조 규칙:`에 적합도 함수 task가 있었으면 그 검사가 **1단계 오라클 출력에서 실제 실행됐는지**, 그리고 **위반 주입 시 red 확인**이 build 보고에 있는지 본다 — 없으면 강제가 증명되지 않은 것이다.
   - plan **미해결·전제**에 `검증 필요`로 남은 항목이 build 중 해소됐는지 — 안 됐으면 advisory 최상단에 올린다.
   - **`수정 지점` 이력 대조**(이번 plan의 `## 접근`이 뿌리가 아닌 고리에서 고쳤을 때만 — 뿌리에서 고쳤으면 건너뛴다). `grep -rn "수정 지점" .plans/`로 과거 plan의 기록을 모아 **같은 뿌리를 가리키는 기록이 반복되는지** 본다. 반복되면 그 기록들은 이유가 아니라 **알리바이**다 — 근인 수정이 관행이 됐고 부채가 복리로 쌓인다는 신호이므로, 뿌리·반복 횟수·해당 plan 목록을 묶어 advisory 최상단에 올린다. 단발이면 올리지 않는다(예외 한 번은 예외다). **여기서 고치지 않는다** — 뿌리를 칠지는 이 리뷰의 안건이 아니라 다음 plan의 안건이다.

3. **diff 자체 검토 — fresh-context `jay-flow:reviewer`에 위임.** 연속 주행이면 이 시점의 메인은 구현·단순화 잔해로 컨텍스트가 가장 더럽고, 자기가 고친 코드를 자기 합리화 위에서 검토하게 된다 — build가 구현을 메인에게 안 시키는 것과 같은 이유(컨텍스트 위생)로, 이 단계는 메인이 직접 하지 않는다. reviewer는 **세션 모델을 상속**한다(바꾸는 건 모델이 아니라 컨텍스트다). lens fan-out 재도입이 아니다 — 축을 여럿으로 흩는 게 아니라 깨끗한 눈 하나다.
   - reviewer에 넘긴다: diff 범위(체크포인트 커밋 목록), 최신 버전 plan 경로, repo 경로, (plan `구조 기준:`에 `범용`이 들어가면) 범용 구조 규칙 문서의 절대 경로와 인용된 규칙 번호·범위(`${CLAUDE_PLUGIN_ROOT}/reference/structure-rules.md`), 검토 축(잠재 에러 — plan 때 못 본 것 포함 / 고위험 표면 테스트 도달 / 구조 규칙 위반(소유자 우회·역방향 의존) / 상태·실행 모델 이탈 / 경계 로그 누락 / 단순화 pass가 놓친 우발적 복잡도). plan 잠재 에러가 위험 패턴을 골랐거나 diff가 고위험 표면(권한·schema/persistence·concurrency·자원 한도·되돌리기)을 건드리면 위험 패턴 카탈로그의 절대 경로(`${CLAUDE_PLUGIN_ROOT}/reference/risk-patterns.md`)도 넘긴다(단독 리뷰도 같은 조건).
   - **reviewer가 트리를 안 바꿨는지 확인한다.** 호출 직전과 직후에 트리 지문 `{ git rev-parse HEAD; git diff --cached --binary; git diff --binary; git ls-files -o --exclude-standard -z | xargs -0 shasum -a 256; } | shasum -a 256`과 **검토 대상 plan 파일(경로·버전)의 내용 hash**를 떠서 비교한다 — status 문자열만 보면 이미 수정된 파일의 내용 변경을 못 잡고, `.plans/`는 ignored라 트리 지문에 안 들어간다. reviewer는 Bash를 가진다. 다르면 그 리뷰는 무효고, 바뀐 경로를 보고한다(자동으로 되돌리지 않는다).
   - **동기로 호출한다**(`run_in_background: false`, 이름 붙이지 않음). 리뷰 결과가 다음 행동을 정하므로 메인이 트리를 건드릴 일이 없다 — 백그라운드로 띄우면 결과 수거 왕복만 생기고, 그 사이 쓰기가 끼면 리뷰가 무효다.
   - 반환된 발견은 메인이 근거를 확인해 advisory에 통합한다 — 그대로 싣지 않는다. 여기서 고치지 않는 것은 동일(고치면 리뷰가 무효).

4. **보고.** 발견을 심각도와 함께 나열(6단계 학습 제안이 있으면 같이) — advisory다, 머지 판정은 사용자. 근거 없는 발견은 만들지 않는다(없으면 없다고). build에서 자동 연결로 진입했어도 **여기서 멈춘다 — accept를 자동으로 하지 않는다**(review 판정이 뒤쪽 사람 게이트다). 예외는 하나 — 사용자의 accept 위임 원문이 roadmap에 기록된 경우다(plan 스킬 roadmap 3). 그때도 발견이 실제 결함이거나 고위험 표면 `안 닿음`·`얕음`이면 수정 → 5단계의 변경 범위 재리뷰를 거친 뒤에만 accept하고, 위임 accept였다는 사실과 발견 분류를 roadmap 실행 기록에 남긴다.

5. **done.** 사용자 accept(또는 4단계 조건을 충족한 위임 accept) 시 **최신 버전** plan 파일에 `status: done`. 리뷰 이후 plan 내용(계약·소유 보정)이 바뀌었으면 기존 리뷰로 accept하지 않고 바뀐 계약으로 2단계부터 다시 대조한다. 단 리뷰 이후 트리가 바뀌었으면(발견 수정 등 — 3단계 지문과 다르면) accept 전에 전체 오라클을 다시 돌리고, **바뀐 범위만 3단계 절차로 reviewer에 다시 넘긴다** — 검증과 리뷰는 리뷰한 그 소스에만 묶이므로, 리뷰 안 된 변경을 오라클 green만으로 done에 싣지 않는다. 바뀐 범위가 공유 불변식에 닿으면 그 불변식의 기존 호출 경계도 재리뷰 범위에 넣는다. 이 plan을 기다리는 `on-hold` plan이 있으면(`grep -rln "on-hold — <이 plan slug>" .plans/`) 재개할 차례라고 한 줄로 알린다 — 재개는 그 plan의 새 버전이다. 남은 advisory 발견은 같은 파일 하단에 기록해 둔다(다음 작업의 씨앗). accept와 함께 **체크포인트 커밋 정리를 한 줄로 묻는다** — squash할지 그대로 둘지(build 규칙대로 squash는 사용자 몫, 임의로 하지 않는다). 위임 accept면 묻지 않고 사용자 복귀 후 인계 보고에 모은다. roadmap 위임 중이면 accept 뒤 roadmap `## 실행 기록`에 plan 종료·실제 총소요·남은 plan 재추정을 한 줄로 남긴다.

6. **학습 제안 (4단계 보고에 포함, 영속은 승인 시만).** 이번 작업에서 **다음 작업의 재조사나 회귀를 실제로 줄일 durable 지식**만 뽑는다 — 틀렸던 전제의 교정 / 자명하지 않거나 반복되는 실패 원인 / 앞으로의 검증 방법을 바꾸는 것 / 프로젝트에 관련된 플랫폼·라이브러리의 안정적 동작 / 안정된 경계나 그 예외. 구현 이력·작업 경과는 지식이 아니다. 있으면 보고에 **영속 제안**을 붙인다: 무엇을 / 어디에 — 아키텍처 불변식은 `ARCHITECTURE.md`(범용 규칙을 적용한 구조 plan이면 그 초안 형식은 `structure-guide.md` §13), 재사용할 기술·프로젝트 지식은 기존 지식 문서(없으면 `docs/LEARNINGS.md` 제안), 한 변경에 묶인 설계 근거는 그 설계 문서. README는 기본 대상이 아니다. 기존 지식과 **충돌하면 덮어쓰지 말고 충돌을 드러낸다.** 범용 구조 규칙 자체가 이 프로젝트에서 틀렸거나 빠진 것이 드러나면(규칙대로 했더니 더 나빠짐, 규칙이 답하지 않는 경계) 프로젝트 문서가 아니라 **플러그인 `reference/` 개정 제안**으로 따로 적는다 — 무엇이 어느 규칙과 부딪혔는지, 실제 코드 근거와 함께. 워크플로 이력·모델 추론·에이전트 정체·AI 사용 흔적은 쓰지 않는다 — 사람 엔지니어가 썼어도 자연스러운 프로젝트 지식만. **명시 승인 없이 쓰지 않는다**(repo 쓰기가 막혀 있어도 제안은 대화로 낸다). roadmap 위임 중이면 사용자가 없으므로 제안을 roadmap `## 학습`에 근거 위치와 적용 조건과 함께 적어 다음 builder dispatch에 쓰고, repo 문서 영속은 사용자 복귀 후 승인을 받는다. 없으면 말없이 건너뛴다.
