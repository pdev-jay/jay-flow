# jay-flow: review

핵심 원리: **오라클 먼저, 사람 판정.** 기계가 판정할 수 있는 것(test/type/build)을 먼저 다 짜내고, 그 위의 발견은 advisory로만 얹는다 — 게이트가 아니다.

## 절차

1. **전체 오라클.** test/type/build 실행. red면 리뷰가 아니라 수리가 먼저다 — build로 돌려보낸다.

2. **diff vs plan.** consolidated diff = **build 시작 시점 HEAD → 최신 체크포인트의 커밋 범위**(build 마무리 보고의 체크포인트 커밋 목록, 없으면 `git log`로 재구성 — 체크포인트 커밋 이후 working tree는 깨끗하므로 `git diff` 단독은 빈 결과가 나온다). 이를 **최신 버전** plan과 대조:
   - 초과 구현(plan에 없는 것) / 누락(plan에 있는데 안 함) / 이탈(다르게 함) 목록.
   - 버전이 여러 개면 v1→vN의 `변경:` 이력을 먼저 훑는다 — diff가 plan과 달라도 **버전 이력에 있으면 승인된 변경, 없으면 이탈**이다.
   - plan의 **잠재 에러** 섹션에 적힌 시나리오가 실제로 처리됐는지 하나씩 확인 — 각 항목의 `검증:` 표기 기준으로(테스트라면 그 테스트가 존재하고 **1단계 오라클 출력에서 실제 수집·실행됐는지** — 전체 green은 그 테스트가 돌았다는 증명이 아니다, skip이면 미검증 취급. `미검증`이면 지금도 미검증인지 명시).
   - plan **미해결·전제**에 `검증 필요`로 남은 항목이 build 중 해소됐는지 — 안 됐으면 advisory 최상단에 올린다.

3. **diff 자체 검토 — fresh-context `jay-flow:reviewer`에 위임.** 연속 주행이면 이 시점의 메인은 구현·단순화 잔해로 컨텍스트가 가장 더럽고, 자기가 고친 코드를 자기 합리화 위에서 검토하게 된다 — build가 구현을 메인에게 안 시키는 것과 같은 이유(컨텍스트 위생)로, 이 단계는 메인이 직접 하지 않는다. reviewer는 **세션 모델을 상속**한다(바꾸는 건 모델이 아니라 컨텍스트다). lens fan-out 재도입이 아니다 — 축을 여럿으로 흩는 게 아니라 깨끗한 눈 하나다.
   - reviewer에 넘긴다: diff 범위(체크포인트 커밋 목록), 최신 버전 plan 경로, repo 경로, 검토 축(잠재 에러 — plan 때 못 본 것 포함 / 고위험 표면 테스트 도달 / 단순화 pass가 놓친 우발적 복잡도).
   - 반환된 발견은 메인이 근거를 확인해 advisory에 통합한다 — 그대로 싣지 않는다. 여기서 고치지 않는 것은 동일(고치면 리뷰가 무효).

4. **보고.** 발견을 심각도와 함께 나열 — advisory다, 머지 판정은 사용자. 근거 없는 발견은 만들지 않는다(없으면 없다고). build에서 자동 연결로 진입했어도 **여기서 멈춘다 — accept를 자동으로 하지 않는다**(review 판정이 뒤쪽 사람 게이트다).

5. **done.** 사용자 accept 시 **최신 버전** plan 파일에 `status: done`. 남은 advisory 발견은 같은 파일 하단에 기록해 둔다(다음 작업의 씨앗). accept와 함께 **체크포인트 커밋 정리를 한 줄로 묻는다** — squash할지 그대로 둘지(build 규칙대로 squash는 사용자 몫, 임의로 하지 않는다).
