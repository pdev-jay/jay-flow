# 범용 구조 규칙

목표는 코드의 위치, 실행 경로, 상태·자원의 소유자, 변경의 영향 범위를 예측할 수 있게 하는 것이다. 세부와 근거는 같은 폴더 `structure-guide.md`의 해당 절(§)에 있고, 아래 "읽을 때"가 걸리면 그 절을 먼저 읽는다.

이 규칙은 프로젝트의 `ARCHITECTURE.md`, 완료된 구조 plan, 실측한 기존 관례가 답하지 않는 곳에 적용한다. 그 셋과 다르면 그 셋이 우선한다. 단, 승인된 구조 plan이 목표 기준으로 이 규칙을 명시적으로 채택하면 그 plan의 범위에서는 이 규칙이 기준이다.

## 경계
1. 코드는 Feature별로 모으고, Feature 안에서는 Presentation · Application · Domain · Data로 책임을 나눈다. 필요한 레이어만 둔다. 나누는 단위는 폴더·패키지이고, 빌드 모듈 분리는 §14 트리거가 참일 때만 한다(§1, §14).
2. 의존 방향은 `App → Feature`, `App → core`, `Feature → core`뿐이다. Feature끼리, core에서 위로는 참조하지 않는다(§2, §4).
3. Domain은 UI·플랫폼 API·Data 구현을 참조하지 않는다(§4).
4. Feature는 작은 공개 API로만 밖과 닿는다. 다른 Feature의 상태가 필요하면 소비하는 쪽이 읽기 계약을 정하고 App이 연결한다(§5, §11).
5. 공용 기술 구현(HTTP 클라이언트, DB 연결, 위치, 시계, 공용 기기 자원 관리)은 core에 둔다. 한 Feature만 쓰는 서버·기기 어댑터는 그 Feature의 Data에 둔다. 업무 규칙과 업무 데이터의 소유권은 담당 Feature에 남긴다(§2).
6. Feature 내부 객체는 그 Feature가 조립한다. 판단·변환·수명 관리 없이 호출만 넘기는 클래스는 만들지 않는다. Feature 경계의 타입을 번역하는 Bridge는 예외다(§1, §6, §11).
7. 런타임 경계(UI 런타임과 네이티브, 공유 코드와 플랫폼 코드, 별도 프로세스 등)를 넘는 호출은 Feature 공개 API나 core 공용 기술 계약으로만 한다. 계약은 한 곳에서 정의해 양쪽 코드를 생성하고, 생성 도구가 없으면 계약 테스트로 대조한다. 소유자와 Coordinator는 그 작업이 실행되는 진입점과 유지 범위로 배치한다(§17).

## 소유와 수명
8. 상태와 자원마다 소유자는 하나다. 플랫폼 자원 API는 소유자만 호출한다(§9).
9. Store는 화면 수명, Controller는 소유하는 상태·자원의 유지 범위, 세션 객체는 작업 수명이다. 수명이 화면보다 길거나 호출자가 둘이면 Controller로 옮긴다(§1, §7).
10. 같은 작업을 제어하는 호출자는 같은 소유자에 연결한다. 종료를 위해 새 소유자나 세션을 만들지 않는다(§8).
11. 자원은 단일 소유자를 통해 쓴다. 사용권은 §14의 트리거가 참일 때 추가하고, 작업·세션 수명에 붙여 실패·취소 경로에서도 반환한다(§9, §14).

## 흐름
12. 확정 결과의 후속 작업은 확정 저장에 성공한 뒤에만 하고, 저장이 실패하면 하지 않는다. 실시간 경고는 저장을 기다리지 않고, 실시간 값은 상태로 바로 내보낸다. 자원 제어의 시작·중지 순서는 자원 계약과 작업별 실패 정책으로 정한다(§3, §9, §16).
13. 여러 Feature에 걸쳐 순서나 실패 정책이 있는 작업은 작업별 Coordinator가 공개 API로 조율한다. Coordinator는 업무 규칙을 갖지 않는다(§10, §12).
14. State는 관찰하고, Command는 직접 호출하고, Event는 소유자가 사실 스트림으로 내보낸다. 전역 EventBus는 두지 않는다(§11).
15. 반드시 수행할 후속 작업은 스트림 수신에만 맡기지 않는다(§11).

## 변경할 때
16. 공개 API·Bridge·Coordinator·자원 소유자는 정한 형식의 경계 로그를 남긴다. 로그는 생성 코드나 래퍼, 공용 로그 함수가 쓰고 민감 정보는 그 함수에서 가린다(§18).
17. §14 표의 항목(Domain·입출력 계약·Controller·사용권·Coordinator·공개 사실 스트림·Feature·영역 묶음)을 새로 만들 때는 그 트리거와 근거 한 줄을 남긴다. 근거를 적지 못하면 만들지 않는다.
18. 규칙을 새로 세우면 §15의 강제 수단을 함께 건다. 위반을 일부러 넣어 실패하는 것을 한 번 본다.

## 읽을 때
| 이런 작업이면 | 먼저 읽는다 |
|---|---|
| 자원 소유자·사용권·시작과 종료·콜백·취소·선점·가용성·백그라운드 동작, 또는 그 호출부를 만들거나 고친다 | §7–9, §16 |
| 앱 재실행·복원 경로나 객체의 생성·해제 시점을 정한다 | §7, §16 |
| 저장과 후속 작업, 처리 대기 기록을 다룬다 | §3, §11 |
| 상태·사실 스트림이나 Command 계약을 만들거나 고치고, 구독·관찰·Feature 간 연결을 바꾼다 | §5, §11 |
| 여러 Feature에 걸친 작업이나 Coordinator를 만든다 | §10, §12 |
| Feature 내부 객체·입출력 계약·어댑터·조립 코드를 추가하거나 연결을 바꾼다 | §1, §2, §4–6 |
| 모듈·Feature·레이어를 새로 나눈다 | §2, §4, §14 |
| 소유자·공개 API·Bridge·Coordinator를 만들거나 바꾼다 | §13, §18 |
| 런타임 경계를 넘는 계약이나 그 양쪽 구현을 만들거나 고친다 | §5, §17 |
| 구조 경계나 상태·자원·작업 흐름의 동작 계약을 바꾼다 | §15의 해당 검증 항목 |
