# 범용 구조 가이드

`structure-rules.md`의 세부와 근거다. 이 문서에서 `ARCHITECTURE.md`는 이 구조를 적용한 프로젝트 repo 루트의 문서를 말한다(§13).

이 아키텍처는 **기능별로 코드를 모으고, 기능 내부에서는 책임을 나누며, 여러 기능에 걸친 작업은 명시적으로 연결하는 구조**다.

목표는 모든 작업에 같은 클래스와 호출 순서를 강제하는 것이 아니다. **코드의 위치, 실행 경로, 상태와 자원의 소유자, 변경의 영향 범위를 예측할 수 있게 만드는 것**이다.

구조는 가장 적은 구성으로 시작한다. §14 표에 있는 분리는 그 트리거가 참이 되었을 때만 추가한다. 규칙은 §15의 확인 방법으로 지킨다.

## 1. Feature와 Layer를 구분한다.

Feature는 로그인·러닝·기기·기록처럼 기능을 나누는 경계다. Layer는 각 기능 내부에서 책임을 나누는 기준이다.

Feature와 Layer는 코드의 논리 경계다. 기본은 빌드 모듈 하나(앱 모듈, 앱 타깃) 안에서 폴더·패키지로 나눈다. 빌드 모듈(Gradle 모듈, SwiftPM 타깃)로 나누는 것은 §14의 빌드 모듈 분리 트리거가 참일 때만 한다.

| 레이어 | 책임 | 예시 |
|---|---|---|
| Presentation | 입력 수집과 화면 표시 | Screen, UI 컴포넌트 |
| Application | 요청 처리, 작업 조율, 상태와 세션 수명 관리 | Store, Controller, Handler |
| Domain | 업무 규칙과 판단 | 시작 조건, 거리 계산, 기록 검증 |
| Data | 외부 입출력 구현 | Repository 구현, 서버·DB·기기 어댑터 |

Application의 세 이름은 수명으로 구분한다.

| 이름 | 수명 | 하는 일 |
|---|---|---|
| Store | 화면 수명 | 화면 상태를 들고, 업무 상태를 관찰해 화면 형태로 바꾼다. 업무 상태가 이 화면 안에서만 살고 이 화면만 바꾸면(§14 Controller 트리거가 거짓) Store가 업무 상태를 직접 들어도 된다. 트리거가 참이 되면 그 상태를 Controller로 옮기고 Store는 관찰만 한다 |
| Controller | 소유하는 상태·자원의 유지 범위(앱, 로그인 등). 화면보다 길 수 있다 | 업무 상태와 자원 사용의 소유자다. 개별 작업 세션 객체는 작업 수명으로 따로 만들고 끝낸다(§7) |
| Handler | 요청 하나 | 상태를 들지 않고 요청 하나를 처리하고 끝난다 |

Feature 안에는 책임이 실제로 있는 레이어만 둔다. Presentation·Application·Data는 그 책임(화면, 요청 처리·상태, 외부 입출력)이 생기면 두고, Domain은 §14의 트리거가 참일 때만 분리한다. 판단·변환·수명 관리 없이 호출을 그대로 넘기기만 하는 클래스는 만들지 않는다.

## 2. App은 기능들을 조립하고 연결한다.

App은 다음을 담당한다.

- 외부 구현과 Feature 연결
- 앱 초기화와 화면 이동
- 앱 전체 인증 세션의 연결과 관리
- 여러 Feature에 걸친 작업 조율

외부 구현의 위치는 종류와 사용 범위로 정한다.

- 기술 구현(HTTP 클라이언트, DB 연결, 위치, 시계, 여러 Feature가 쓰는 기기 자원 관리)은 계약과 구현을 공용 영역(`core`)에 둔다.
- 한 Feature만 쓰는 서버·기기 어댑터는 그 Feature의 Data에 둔다. 사용 범위가 넓어진 기술 구현은 `core`로 옮길 수 있다.
- 업무 규칙과 업무 데이터(예: 러닝 기록 Repository)의 소유권은 여러 기능이 쓰더라도 해당 Feature에 남긴다. 다른 기능에는 공개 API나 읽기 계약으로 제공한다.

App은 Feature와 `core`를 참조해 구현을 조립한다. Feature는 `core`를 참조할 수 있지만 App과 다른 Feature는 참조하지 않는다. `core`는 App과 Feature를 참조하지 않는다. 인스턴스 수와 공유 범위는 §7의 수명 기준으로 정한다.

App은 모든 호출이 통과하는 중간 단계가 아니다. 프로필 조회나 러닝 내부 계산처럼 한 기능에서 끝나는 작업은 해당 Feature에서 처리한다.

## 3. 실행 경로는 작업에 필요한 책임만 거친다.

대표적인 실행 흐름은 다음과 같다.

- 단순 조회: Screen → Store → Repository → 외부 시스템
- 업무 판단이 있는 작업: Screen → Controller 또는 Handler → Domain 판단 → 외부 입출력
- 교차 기능 작업: 요청 → Coordinator → 각 Feature의 공개 API

`Feature → App → Domain → Data`라는 고정 순서를 사용하지 않는다. Feature와 App은 코드의 영역이고, Domain과 Data는 책임 구분이기 때문이다.

한 작업 안에서 외부 입출력의 순서는 결과의 종류로 정한다.

| 종류 | 예시 | 순서 |
|---|---|---|
| 확정 결과의 후속 작업 | 완료 소리, 동기화 요청, 다른 Feature 통지 | 확정 저장이 끝난 뒤에 한다. 저장이 실패하면 하지 않고 실패를 호출자에게 돌려준다 |
| 실시간 경고 | 심박 상한 경고, 연결 끊김 진동 | Domain 판단 직후에 한다. 저장을 기다리지 않는다 |
| 자원 제어 | 센서 시작·중지, 스캔, 백그라운드 실행 | 사용권과 수명 규칙(§9)을 따른다. 저장 결과와 별개로 정한다 |
| 실시간 값 | 센서 샘플, 진행률 | 상태로 바로 내보낸다 |

저장이 실패하면 이미 바꾼 메모리 상태는 이전으로 되돌리거나, 처음부터 저장 성공 뒤에 바꾼다. 저장 실패 때 자원을 유지할지(예: 다시 시도를 위해 센서를 켜 둘지)는 그 작업의 실패 정책으로 정한다.

## 4. 실행 흐름과 코드 의존성을 구분한다.

런타임에 데이터를 요청하는 경로와 소스 코드가 참조하는 방향은 다를 수 있다.

- Presentation은 Application의 입력·상태 계약을 사용한다.
- Application은 Domain과 필요한 입출력 계약을 사용한다.
- Domain은 UI, 플랫폼 API, Data 구현을 참조하지 않는다.
- Data는 필요한 입출력 계약을 구현하고 외부 시스템에 접근한다.
- 조립 코드는 계약에 실제 구현을 연결한다.

입출력 계약은 사용하는 책임에 따라 Application 또는 Domain에 둔다. 앱 전체 공용 외부 구현의 계약은 `core`에 둔다(§2). 계약(인터페이스)은 §14의 트리거가 참일 때만 만든다.

의존 방향은 `App → Feature`, `App → core`, `Feature → core`다(폴더·패키지 기준이고, 빌드 모듈로 나눴으면 모듈 기준). Feature끼리는 서로 참조하지 않고, App이 공개 API와 읽기 계약을 연결한다(§5, §11).

## 5. Feature는 공개 계약을 통해 외부와 연결한다.

외부에 제공할 기능은 작은 공개 API로 표현한다.

예를 들어 Running은 `start()`, `stop()`, 현재 상태 스트림, 발생한 사실 스트림을 제공하고, 내부 Controller·Repository·세션 객체는 감춘다.

Feature는 다른 Feature의 내부 Store나 구현 객체를 직접 참조하지 않는다. 여러 기능을 연결하는 코드는 각 기능의 공개 API를 사용한다.

Feature에서 App으로 요청을 전달할 때도 주입된 인터페이스나 콜백을 사용한다. Feature가 App의 구체적인 Coordinator를 직접 참조하지 않는다.

## 6. 각 Feature는 자신의 내부 객체를 조립한다.

Feature의 조립 코드인 Component 또는 DI 모듈은 내부 객체의 생성과 연결을 담당한다.

Running을 예로 들면 다음과 같다.

| 조립 담당 | 연결하는 내용 |
|---|---|
| App | 위치 구현·저장소·시계를 Running에 제공 |
| RunningComponent | Repository·Controller·API 구현 생성 및 연결 |
| RunningController | 실행 중인 러닝 세션 생성과 종료 |

Feature 내부에 객체가 추가되면 해당 Feature의 조립 코드를 수정한다. 공개 계약이 그대로라면 App의 연결 코드는 유지할 수 있다.

Component는 조립 담당이다. 실제 `start()`나 `stop()` 호출이 Component를 경유할 필요는 없다.

## 7. 생성 시점과 유지 범위를 별도로 정한다.

Coordinator가 어떤 Feature를 사용한다고 해서 그 Feature의 모든 객체를 앱 시작 때 생성하지 않는다.

객체마다 다음을 정한다.

- 언제 생성하는가: 앱 시작, 첫 사용, 사용자 로그인, 작업 시작
- 언제 해제하는가: 화면 종료, 작업 종료, 로그아웃, 프로세스 종료
- 누가 동일한 객체를 공유하는가

가벼운 관리자나 API는 유지하고, 실제 작업 세션은 필요할 때 생성할 수 있다. RunningController는 유지하면서 RunningSession은 `start()` 때 생성하고 `stop()` 때 제거하는 식이다.

플랫폼이 앱을 다시 실행하는 진입점(예: iOS BLE 상태 복원, Android 프로세스 재시작)에서 살아 있어야 하는 소유자는 화면 진입이 아니라 앱 실행 진입점에서 만든다(§16).

`lazy`나 provider는 생성 시점을 늦추는 수단이다. 객체의 유지 범위와 해제 정책까지 자동으로 해결하지는 않는다.

Controller와 공유 자원 소유자는 소유자 표(§13)에 생성 시점, 해제 시점, 공유 범위를 한 줄로 적는다.

## 8. 같은 작업을 제어하는 호출자는 동일한 소유자에 연결한다.

화면이 시작한 러닝을 로그아웃 Coordinator도 종료할 수 있어야 한다. 두 호출자는 같은 러닝 관리자에 연결되어야 한다.

종료를 위해 새로운 러닝 관리자나 세션을 만들지 않는다. 실행 중인 세션이 없다면 종료 요청은 새 작업을 만들지 않고 반환한다. 단, 프로세스 종료를 넘어 저장된 재개 의도가 있으면 그것을 해제한다(§16).

공유 여부는 객체의 이름이 아니라 관리하는 상태와 자원의 수명을 기준으로 결정한다.

## 9. 상태와 자원에는 단일 소유자를 둔다.

같은 사실을 여러 Store에서 독립적으로 변경하지 않는다.

- 러닝 세션 소유자는 실제 러닝 상태를 변경한다.
- 화면 Store는 그 상태를 관찰하거나 화면 표시 형태로 변환한다.
- 인증 세션 소유자는 로그인 상태를 확정한다.

업무 상태와 화면용 상태는 구분한다. 화면이 종료되어도 백그라운드 작업이 계속되어야 한다면, 그 작업의 소유자를 화면 수명에 묶지 않는다.

위치 추적·BLE·송신 루프 같은 공유 자원은 다음을 따른다.

- 플랫폼 API(`BluetoothGatt`, `BluetoothLeScanner`, `CBCentralManager`, 위치 API 등)는 그 자원의 소유자만 호출한다.
- 사용권은 §14의 사용권 트리거가 참일 때 둔다. 거짓이면(자원을 시작·중단하는 경로가 하나이거나, 여럿이어도 수명이 같으면) 사용하는 쪽은 소유자의 시작·중지를 직접 호출하고, 소유자가 그 수명을 관리한다.
- 사용권을 두면 사용하는 쪽은 소유자에게서 사용권을 받고, 끝나면 사용권을 반환한다. 반환은 실패·취소 경로에서도 일어나야 한다.
- 사용권을 두면 소유자는 남은 사용권을 보고 자원 설정을 정한다. 사용권 반환으로 자원을 멈출 때는 마지막 사용권이 반환된 뒤에만 멈춘다. 그래서 한 사용자의 해제가 다른 사용자의 작업을 중단하지 않는다. 예외는 둘이다. 가용성 상실(권한·무선 전원 변경)과, §16에 적어 둔 선점 정책에 따른 선점이다.
- 사용권의 수명은 화면이 아니라 작업이나 세션에 붙인다.

소유자가 동시 요청, 취소, 플랫폼 콜백, 복원을 어떻게 다루는지는 §16의 동작 계약으로 정한다.

## 10. Coordinator는 여러 기능의 작업 절차를 소유한다.

Coordinator에는 다음을 명시한다.

- 요청할 작업과 실행 순서
- 동시에 수행해도 되는 작업
- 완료 판단 기준
- 실패·취소·타임아웃 처리
- 중복 요청과 재시도 정책

실제 업무 규칙과 자원 정리는 각 Feature가 수행한다. Coordinator가 러닝 계산이나 BLE 연결 구현까지 가져오지 않는다.

예를 들어 로그아웃은 다음처럼 연결할 수 있다.

`신규 작업 차단 → 러닝·기기 정리 → 인증정보 삭제 → 로그아웃 상태 확정`

이 순서와 실패 시 행동은 서비스 정책으로 정한다. 정리 실패 때문에 로그아웃을 무조건 막거나, 실패를 무조건 무시하는 규칙을 일괄 적용하지 않는다. 정한 정책은 Coordinator마다 단계별 표(단계 | 실패 시 | 취소 시 | 타임아웃)로 남기고, 표의 각 칸을 테스트로 건다.

완료를 확인해야 하는 API는 단순히 신호를 보내는 것과 구분한다. 반환 시점에 무엇이 완료되어 있는지 계약에 명시한다.

## 11. State·Event·Command를 구분한다.

| 종류 | 의미 | 예시 | 전달 방식 |
|---|---|---|---|
| State | 현재 상태 | 로그인됨, 러닝 중 | 소유자가 공개 API의 상태 스트림으로 내보낸다. 스트림은 새 구독자에게 현재 상태를 먼저 주고 이후 변경을 전달한다. 조회한 뒤 구독하는 방식으로 현재 상태를 맞추지 않는다. 같은 Feature 안에서는 직접 관찰한다. 다른 Feature가 보려면 소비하는 쪽이 필요한 만큼의 읽기 계약을 정하고, App이 그 계약을 원본 소유자의 상태 스트림에 연결한다 |
| Event | 발생한 사실 | 세션 만료, 운동 완료 | 소유자가 공개 API의 사실 스트림으로 내보낸다. 다른 Feature에서 받아 작업을 일으키는 쪽은 Coordinator다 |
| Command | 수행 요청 | 로그아웃 요청, 러닝 종료 요청 | 받는 쪽의 공개 API를 직접 호출한다 |

현재 상태가 필요하면 상태를 관찰한다. 작업과 완료 확인이 필요하면 명시적으로 요청한다.

다른 Feature의 결과를 보여 주기만 하는 쪽(기록 목록, 통계)은 Event를 구독하지 않고, 저장된 데이터나 상태를 관찰한다.

App의 연결 코드(Bridge)는 Feature 경계에서 타입을 번역하므로 §1의 "넘기기만 하는 클래스" 금지에 해당하지 않는다.

전역 EventBus를 두지 않는다. 순서가 중요한 작업을 구독자의 반응에 맡기지 않는다.

사실 스트림은 그 순간 구독 중인 쪽에만 닿는다. 프로세스 종료나 구독 시점과 관계없이 반드시 수행해야 하는 후속 작업은 스트림 수신에만 맡기지 않는다.

- 사실을 만든 Feature는 확정 저장과 같은 트랜잭션에 처리 대기 기록을 남긴다.
- 미처리 목록과 처리 완료 표시를 처리 담당이 쓸 수 있게 제공한다. 처리 담당이 다른 Feature나 Coordinator면 공개 API로 제공한다.
- 처리 담당은 작업 범위로 정한다. 한 Feature 안에서 끝나는 후속 작업은 그 Feature의 Application 처리자가, 여러 Feature에 걸친 작업은 Coordinator가 맡는다. 처리 대기 기록이 있다는 이유만으로 Coordinator를 만들지 않는다.
- 처리 담당은 새 기록 알림(처리 담당이 Feature 밖이면 공개 사실 스트림, 같은 Feature 안이면 내부 알림)의 구독을 먼저 활성화한 뒤 미처리 목록을 조회한다. 같은 Feature 안의 처리를 위해 공개 사실 스트림을 만들지 않는다(§14). 그래서 조회와 구독 사이에 유실 구간이 없다. 구독이 끊겼다가 다시 연결되면 미처리 목록을 다시 조회한다. 같은 기록이 조회와 스트림 양쪽으로 올 수 있으므로, 받는 쪽의 처리는 같은 사실을 두 번 받아도 결과가 같아야 한다.
- 처리에 실패하면 처리 담당이 정한 재시도 조건과 지연에 따라 실행 중에도 다시 처리한다. 프로세스가 없는 동안 처리해야 하면 플랫폼의 예약 실행에 연결한다.
- 성공을 확인한 뒤에만 처리 완료로 표시한다. 재시도할 수 없는 실패는 미처리 목록에 남겨 두지 않고 실패 상태로 확정한다.

## 12. 규모가 커지면 조립과 워크플로도 책임별로 나눈다.

기능이 많아지면 관련 Feature를 계정·운동·기록·커뮤니티 같은 영역으로 묶을 수 있다. 영역은 탐색과 소유권을 정리하는 묶음이며, 반드시 통과해야 하는 새 레이어가 아니다.

AppGraph 한 파일에 모든 내부 객체를 조립하지 않는다. Feature별 조립 코드와 작업별 Coordinator를 연결한다.

로그아웃·운동 완료·구매를 하나의 거대한 Coordinator에 합치지 않는다. 작업이 영향을 미치는 범위에 조율 코드를 둔다.

## 13. 구조는 코드 경계와 짧은 문서로 유지한다.

책임별 변경 위치는 다음과 같다.

| 변경 내용 | 먼저 살펴볼 곳 |
|---|---|
| 화면 표시 | Presentation |
| 입력 처리·작업 조율·화면 상태 | Application |
| 업무 조건·계산 | Domain |
| 서버·DB·기기 통신 | Data |
| 여러 기능의 실행 순서 | 해당 Coordinator |
| 구현 연결·생성 범위 | Component 또는 DI 모듈 |

내부 구현은 Feature 안의 폴더·패키지에 두고 §15의 방법으로 밖에서 참조하지 못하게 한다. 빌드 모듈로 나눴으면 접근 제한(예: Kotlin `internal`)으로 감춘다.

`ARCHITECTURE.md`에는 다음을 기록한다. 문서가 있으면 승인된 갱신(작업 계획의 문서 갱신 작업, 또는 리뷰 뒤의 반영 승인)으로 고친다. 없으면 이 항목을 작업 계획에 기록하고, 문서는 별도 승인을 받아 만든다. 문서가 없다는 것 자체는 위반이 아니다.

- 기능 경계와 각 Feature의 공개 API
- 의존성 규칙
- 소유자 표: `상태·자원 | 소유자 | 생성 | 해제 | 공유 범위 | 직렬화 경계`
- Coordinator 목록과 각각의 정책 표(§10)

Controller나 Coordinator가 있는 Feature에는 책임·진입점·공개 API·주요 흐름을 짧게 기록한다.

## 14. 분리를 추가하는 트리거

구조는 가장 적은 구성으로 시작한다. 아래 트리거가 참이 되었을 때만 분리를 추가하고, 그 근거를 한 줄로 남긴다. 근거를 적지 못하면 추가하지 않는다.

| 추가하는 것 | 트리거 | 트리거가 거짓이면 |
|---|---|---|
| Domain | 여러 값에 걸친 업무 규칙이나 상태 전이가 있다 | Application에서 바로 처리 |
| 입출력 계약(인터페이스) | IO·기기·외부 서비스 경계다(테스트 격리), 또는 구현이 둘 이상이다 | 구체 클래스를 직접 사용 |
| Controller | 상태나 자원 사용이 화면보다 오래 살거나, 호출자가 둘 이상이다 | Store 또는 Handler |
| 사용권 (소유자는 트리거와 무관하게 자원마다 하나, §9) | 같은 자원을 시작·중단하는 호출 경로가 둘 이상이고 수명이 다르다 | 소유자 하나, 사용권 없이 |
| Coordinator | 작업이 Feature 둘 이상에 걸치고, 순서나 실패 정책이 있다 | 해당 Feature 안에서 처리 |
| 공개 사실 스트림(Event) | 다른 Feature가 그 사실을 받아 작업을 해야 한다 | 상태 스트림만 |
| Feature 분리 | 독립된 업무 규칙과 업무 데이터를 갖고 다른 Feature 없이 바뀔 수 있다, 또는 같은 단어가 다른 규칙으로 쓰인다 | 같은 Feature 안에서 객체를 나눈다. 수명만 다르면 Controller와 세션 객체로 나눈다 |
| 영역 묶음 | Feature가 많아 탐색이 어렵다 | 묶지 않음 |
| 빌드 모듈(타깃) 분리 | 플랫폼이나 선택한 배포 방식이 별도 타깃·모듈을 요구한다(예: iOS 위젯·공유 확장·알림 서비스 확장처럼 앱과 따로 실행되는 App Extension — Swift의 `extension` 문법이 아니다, Android dynamic feature, 여러 플랫폼이 공유하는 코드), 또는 다른 앱·저장소가 이 코드를 의존해야 한다, 또는 현재 검사로 막지 못한 같은 종류의 경계 위반이 리뷰에서 두 번 나왔다, 또는 여러 사람이 Feature를 나눠 맡아 같은 파일·빌드 설정 충돌이 반복된다. 빌드 시간은 근거가 아니다 — 작은 모듈이 많으면 모듈마다 설정·리소스 처리·코드 생성이 반복되어 오히려 느려진다. Feature 개수도 근거가 아니다 | 빌드 모듈 하나 안의 폴더·패키지로 두고 §15의 import 검사로 경계를 지킨다. 나눌 때도 트리거가 걸린 부분만 뗀다. 첫 분리는 보통 Feature가 아니라 여러 Feature가 쓰는 공유 자원 소유자(`core`)다 |

## 15. 규칙의 확인 방법

규칙은 확인 방법이 있을 때만 지켜진다. 확인 방법은 일부러 위반을 넣었을 때 실패하는 것을 한 번 본 뒤에 유효하다고 본다.

기존 코드라 강제 수단(모듈 분리 등)을 이번 변경에서 세울 수 없으면 보조 검사를 임시로 걸 수 있다. 그때는 보조 검사가 잡지 못하는 범위와, 강제 수단으로 옮길 시점을 함께 적는다.

강제 수단은 위반이 빌드나 테스트를 실패시키는 장치다. 보조 검사는 강제 수단으로 막지 못하는 부분을 grep으로 찾는다.

빌드 모듈을 나누기 전(§14)에는 import 검사 테스트가 §4·§5·§9의 강제 수단이다. 테스트 러너에서 소스 파일을 읽어, 금지된 패키지 경로(예: `com.example.running.application.`)가 import 줄이나 코드 본문에 나오는지 찾는다. 패키지 선언 줄은 제외한다. 위반 주입은 금지된 import 한 줄과, import 없이 완전 수식 이름으로 참조하는 한 줄을 각각 넣어 둘 다 실패하는지 본다. 모듈을 나눈 부분은 빌드 도구의 모듈 의존성과 접근 제어로 옮긴다. 강제 수단을 세우려는 이유만으로 빌드 모듈을 나누지 않는다.

언어마다 이 검사가 닿는 범위가 다르다. Kotlin·Java는 다른 패키지의 타입을 import나 완전 수식 이름으로만 쓸 수 있어서, 둘 다 찾으면 패키지 사이 참조를 대부분 잡는다. 사각지대는 같은 패키지 이름을 쓴 우회와 리플렉션이다. Swift는 같은 타깃 안의 타입을 import 없이 쓰므로 앱 코드 사이의 참조는 잡지 못한다. 시스템 프레임워크(`UIKit`, `SwiftUI`, `CoreBluetooth`, `CoreLocation`)는 직접 import한 파일만 검사된다. bridging header, `@_exported import`, 다른 파일의 import로 멤버가 보이는 경우는 사각지대다. 그래서 `@_exported import`는 금지 패턴에 넣고, 소유자 전용 프레임워크는 bridging header에 넣지 않으며, 원시 API 이름 검사(보조 검사)를 함께 건다. Swift 단일 타깃에서 강제할 수 없는 규칙은 plan에 `강제 수단 미적용: <규칙> — Swift 단일 타깃`으로 적고 리뷰로 확인한다.

| 규칙 | 강제 수단 | 보조 검사 |
|---|---|---|
| §4 Domain은 UI·플랫폼·Data를 참조하지 않는다 | 빌드 모듈 하나: Domain 폴더의 파일에서 플랫폼(예: `android.`, `UIKit`, `SwiftUI`, `CoreBluetooth`), Presentation, Data 패키지 import를 찾는 import 검사 테스트. 모듈을 나눴으면 Domain 모듈의 허용 의존성을 표준 라이브러리와 필요한 계약으로 제한한다. 플랫폼 API, UI 타입, Data 구현 참조를 각각 넣어 실패를 확인한다 | Swift 단일 타깃에서는 Data·Presentation 타입 참조가 import 없이 생기므로 잡지 못한다. 플랫폼 프레임워크 import만 검사되고 나머지는 리뷰로 본다 |
| §4 의존 방향 | 빌드 모듈 하나: 패키지 사이 import 검사 테스트(`core`가 위를 참조, Feature가 다른 Feature나 App을 참조하면 실패). 모듈을 나눴으면 빌드 도구의 모듈 의존성(예: Gradle 모듈, SwiftPM 타깃). 역방향 참조를 넣으면 실패해야 한다 | Swift 단일 타깃에서는 성립하지 않는다. 리뷰로 보고 `강제 수단 미적용`으로 적는다 |
| §5 다른 Feature의 내부 참조 금지 | 빌드 모듈 하나: Feature 밖의 파일에서 그 Feature의 내부 폴더(예: `application`·`domain`·`data`) import를 찾는 import 검사 테스트. Feature를 빌드 모듈로 나눴으면 언어의 접근 제어(예: Kotlin `internal`, Swift 타깃별 `internal`)로 공개 API와 조립 진입점만 노출한다. 숨기려는 Feature 경계보다 넓게 열리는 접근 수준(예: Swift `package`는 같은 package의 다른 타깃에도 열린다)은 Feature 내부 은닉에 쓰지 않는다. App이 Feature 내부 Controller나 Repository 구현을 참조하면 실패해야 한다 | Swift 단일 타깃에서는 강제할 수 없다. 리뷰로 보고 `강제 수단 미적용`으로 적는다 |
| §9 플랫폼 자원 API는 소유자만 | 플랫폼 프레임워크 경로(예: `android.bluetooth`, `CoreBluetooth`, `CoreLocation`)를 소유자 폴더 밖에서 찾는 import 검사 테스트. 소유자를 빌드 모듈로 나눠도 Android의 `android.bluetooth`처럼 플랫폼 SDK가 모든 모듈에 주어지면 모듈 의존성으로 막을 수 없으므로 이 검사를 유지한다. 서드파티 SDK처럼 의존을 그 모듈에만 둘 수 있을 때만 모듈 의존성으로 대신한다 | 원시 API 이름(예: `BluetoothLeScanner`, `CBCentralManager`)을 소유자 경로 밖에서 찾는 grep 테스트. Swift의 재수출·bridging header로 import 없이 보이는 경우를 잡는다. 범위는 repo 전체 |
| §9 사용권 (둔 경우) | 테스트: A와 B가 사용 중일 때 A가 반환해도 B는 계속 동작한다. 실패·취소 경로에서도 반환된다 | 없음 |
| §8 같은 소유자 | 테스트: 화면이 시작한 작업을 Coordinator가 종료하면 세션이 남지 않는다. 실행 중인 세션이 없을 때의 종료는 아무것도 만들지 않는다 | 없음 |
| §3 후속 작업은 저장 뒤 | 테스트: fake 저장소가 실패하면 후속 작업 호출이 0회다. 실시간 경고는 fake 저장소가 멈춰 있어도 나간다 | 없음 |
| §10 Coordinator 정책 | Coordinator마다 정책 표의 각 칸(실패·취소·타임아웃·중복 요청)에 대한 테스트 | 없음 |
| §11 반드시 수행할 후속 작업 | 테스트: 저장 뒤 후속 작업 전에 프로세스를 끝내고 다시 시작하면 처리된다. 같은 사실을 두 번 처리해도 결과가 같다 | 없음 |
| §11 구독과 미처리 조회의 경계 | 테스트: 구독 활성화와 미처리 조회 사이에 사실을 저장·발행해도 재시작 없이 처리된다. 구독이 끊겼다 다시 연결돼도 처리된다 | 없음 |
| §16 선점 (사용권을 둔 경우) | 테스트: 기존 사용권이 남은 상태에서 독점 사용권이 선점하면 기존 사용자에게 중단이 알려지고, 독점 작업이 끝난 뒤 정책대로 재개된다 | 없음 |
| §11 처리 실패 후 재처리 | 테스트: 프로세스를 재시작하지 않은 채 일시 실패 뒤 성공하면 처리 완료가 된다. 재시도 불가능한 실패는 실패 상태로 확정된다 | 없음 |
| §11 상태 스트림의 현재 값 | 테스트: 상태가 바뀐 뒤 새로 구독하면 현재 값을 받는다. 구독을 시작하는 도중의 변경을 놓치지 않는다 | 없음 |
| §16 직렬화 | 테스트(결정적 스케줄러): 시작·종료·연결 완료 콜백의 순서를 교차시켜도 종료 뒤 세션이나 자원이 다시 살아나지 않는다 | 없음 |
| §16 취소 | 테스트: 호출 취소 뒤 도착한 성공 콜백이 자원을 남기지 않는다. 타임아웃 뒤에도 정리가 끝까지 진행된다 | 없음 |
| §16 사용권 호환성 (사용권을 둔 경우) | 테스트: 호환되는 사용권은 함께 동작한다. 호환되지 않는 사용권은 정한 거절·대기·선점 규칙대로 처리된다 | 없음 |
| §16 가용성 변화 | 테스트: 연결·스캔·재연결 도중 권한이나 무선 전원을 잃으면 플랫폼 호출을 멈추고 차단 이유를 내보낸다. 회복하면 정한 정책대로 재개한다 | 없음 |
| §16 프로세스 종료와 복원 | 테스트: 실행 중 프로세스 종료 뒤 재실행하면 저장된 의도를 대조해 재개 또는 중단으로 확정한다. 종료 뒤 `stop()`은 재개 의도를 해제한다. 플랫폼 복원 실행(예: iOS BLE 상태 복원: 화면 없이 실행, 복원 연결과 일반 요청의 경합)은 대상 실행 환경에서 검증한다. 자동으로 재현할 수 없는 부분은 운영 환경에 맞는 수동 절차와 담당자를 적고, 실제 기기에서만 확인할 수 있는 동작에만 실기기 검증을 요구한다 | 없음 |
| §16 백그라운드 실행 조건 | 테스트: 실행 조건을 확보하지 못하면 시작을 거절하거나 예약 작업으로 바꾼다. 실행 기회 종료 시 저장·중단·재개 정책은 대상 실행 환경에서 검증한다. 자동으로 재현할 수 있으면 자동화하고, 재현할 수 없는 부분은 운영 환경에 맞는 수동 절차와 담당자를 적는다 | 없음 |
| §17 런타임 경계 계약 | 계약 정의 하나에서 양쪽 코드를 생성한다. 생성 도구가 없으면 계약 정의와 양쪽 구현을 대조하는 계약 테스트를 둔다. 계약 밖의 직접 호출을 넣으면 빌드나 테스트가 실패해야 한다 | 런타임 경계 API 호출은 생성 코드, 또는 단일 계약 정의에 대한 계약 테스트로 검증된 경계 어댑터 안에서만 허용한다. 이 허용 경로 밖의 직접 호출(예: 화면 코드의 수동 채널 호출)을 찾는 grep 테스트. 허용 경로 밖에 호출을 넣으면 실패하는지 확인한다 |
| §17 소유자의 런타임 | 테스트: 작업에 필요한 진입점마다(UI 런타임이 없는 진입점 포함) 소유자와 Coordinator가 동작한다. 여러 런타임·프로세스가 있어도 같은 자원의 소유자가 둘 생기지 않는다 | 없음 |
| §17 여러 구현의 동작 일치 | 같은 시나리오(입력 순서와 기대 상태)를 각 구현에 돌리는 공유 시나리오 테스트 | 없음 |
| §18 경계 로그 | 공개 API는 로그 래퍼를 거쳐서만 노출되도록 조립 코드에서 막는다. 테스트: fake로 흐름 하나를 돌리면 기대한 경계 로그가 같은 상관 식별자로 순서대로 나오고, 민감 필드는 가려진다. 같은 대상의 같은 연산을 동시에 실행하거나 재시도해도 호출과 결과를 구분할 수 있다 | 경계 파일에서 공용 로그 함수 밖의 로그 API 직접 호출을 찾는 grep 테스트 |
| §11 전역 EventBus 금지 | 없음 | 프로젝트가 쓰는 전역 이벤트 배포 수단의 목록을 정하고, 그 수단으로 앱 전역에 게시하는 곳을 찾는 grep 테스트(예: 전역 SharedFlow, NotificationCenter, 이벤트 버스 라이브러리) |
| §14 트리거 | 없음 | 확인 불가. 구조를 추가하는 변경에 근거 한 줄을 적고 리뷰에서 본다 |

## 16. 자원 소유자의 동작 계약

BLE·위치·백그라운드 작업처럼 오래 살고 플랫폼이 끼어드는 자원의 소유자는 아래 여섯 가지를 정하고(사용권 호환성은 사용권을 둔 경우만), 소유자 표(§13)와 테스트(§15)에 남긴다.

**직렬화.** 명령, 플랫폼 콜백, 타이머가 상태를 바꾸는 경로를 소유자 안의 한 실행 경계(단일 디스패처, actor 등)로 모은다. 긴 입출력을 기다리는 동안에도 종료 요청을 받을 수 있어야 한다. 입출력 결과를 반영할 때 작업 식별자나 세대를 확인하고, 종료되거나 교체된 작업의 늦은 콜백은 상태를 바꾸지 않는다.

**취소.** 자원 작업 API는 호출자의 대기 취소, 실제 작업 취소 요청, 실제 종료 완료를 구분해 계약에 적는다. 호출자가 취소하거나 타임아웃이 나도 소유자는 늦은 성공 콜백과 남은 자원을 정리한다. 마지막 사용권의 정리는 호출자 취소로 중단되지 않는다. 즉시 멈출 수 없는 작업(펌웨어 갱신 단계 등)은 안전한 중단 지점과 그동안의 자원 점유를 적는다.

**사용권 호환성 (사용권을 둔 경우).** 사용권에는 대상과 필요한 동작 조건(스캔 필터, 연결, 독점 여부)을 담는다. 소유자는 동시에 만족할 수 있는 요구의 병합 규칙과, 만족할 수 없는 요구의 거절·대기·선점 규칙을 정한다. 펌웨어 갱신처럼 독점이 필요한 작업은 독점 사용권을 받는다. 사용권을 두지 않은 소유자는 독점 작업 중에 들어온 시작 요청을 정한 거절·대기 규칙으로 처리한다. 선점할 때 소유자는 기존 사용자에게 중단 또는 대기 상태를 알리고, 실제 자원 동작을 끝내거나 재설정한 뒤 독점 작업을 시작한다. 기존 사용권을 유지할지 무효화할지, 독점 작업이 끝난 뒤 재개할지를 선점 정책에 적는다.

**가용성 변화.** 권한 회수, 무선 전원 꺼짐, 플랫폼 제한은 사용권과 별도로 소유자가 관찰한다. 실행이 불가능해지면 재시도와 플랫폼 호출을 멈추고, 작업 의도는 유지한 채 차단 이유를 상태로 내보낸다. 다시 가능해졌을 때 자동으로 재개할지 사용자에게 다시 물을지는 작업별로 정한다.

**프로세스 종료와 복원.** 프로세스 종료를 넘어 이어 갈 작업은 작업 식별자, 사용자·기기 식별자, 재개 의도, 복구에 필요한 진행 정보를 저장한다. 연결 상태와 사용권은 저장된 값으로 복원하지 않는다. 새 프로세스에서 소유자는 저장된 의도를 실제 플랫폼 상태와 대조해 재개 또는 중단으로 확정하고, 대조가 끝나기 전에는 같은 자원에 새 연결을 시작하지 않는다. 프로세스 종료 때 정리 콜백이 실행된다고 가정하지 않는다. 플랫폼이 자원 상태를 복원하며 앱을 다시 실행하는 경우(예: iOS BLE 상태 복원)에는 앱 실행 진입점에서 같은 복원 식별자로 소유자를 만들고, 복원된 상태를 일반 경로와 같은 소유자에게 연결한다.

**백그라운드 실행 조건.** 객체가 살아 있거나 사용권이 있다고 해서 플랫폼 실행 시간이 보장되지는 않는다. 백그라운드에서 이어지는 작업마다 플랫폼이 허용하는 실행 방식과 그 조건(예: Android의 서비스·예약 실행, iOS의 백그라운드 모드)을 적고, 조건을 확보한 뒤 시작한다. 확보할 수 없으면 시작을 거절하거나 허용된 방식(예약 작업 등)으로 바꾼다. 실행 기회가 끝났을 때의 저장·중단·재개 정책을 정한다.

## 17. 런타임 경계

한 앱 안에 런타임이 둘 이상이면(예: 크로스플랫폼 UI 런타임과 네이티브, 공유 코드와 플랫폼 코드, WebView, 별도 프로세스나 확장) 다음을 따른다.

- 런타임 경계를 넘는 호출은 외부에 공개하도록 정한 계약(Feature 공개 API(§5), core의 공용 기술 계약(§2))으로만 한다. 경계에는 그 계약의 직렬화 형식을 정의하고 내부 구현 객체는 노출하지 않는다. 런타임을 넘는다는 이유만으로 계약이나 업무 데이터의 소유권을 옮기지 않는다.
- 계약은 한 곳에서 정의하고 양쪽 코드를 생성한다. 손으로 양쪽을 맞추는 계약은 두지 않는다. 생성 도구가 없으면 계약 정의 하나와, 양쪽 구현을 그것에 대조하는 계약 테스트를 둔다.
- 경계를 넘는 값과 오류는 경계에서 번역한다. 한쪽 런타임의 타입이나 오류 형식이 다른 쪽 내부로 새지 않고, 오류는 계약에 정의한 형식으로만 넘긴다.
- 소유자(§9)와 Coordinator(§10)의 배치는 그 상태·자원을 쓰는 작업의 실행 진입점과 유지 범위로 정한다. 작업이 백그라운드 재실행, 플랫폼 복원, 푸시·예약 작업처럼 UI 런타임이 뜨지 않는 진입점에서도 실행되면, 그 진입점에서 살아 있는 런타임에 둔다(§7, §16). 화면에서만 필요한 객체는 UI 런타임에 둘 수 있다.
- 여러 런타임이나 프로세스가 같은 상태·자원을 제어하면 권한을 가진 소유자의 실행 위치와 접근 경로를 명시한다. 공통 실행 위치가 없으면 소유권 이전이나 배타적 사용 정책을 정하고, 프로세스마다 만든 객체를 같은 소유자로 보지 않는다. 소유자에 닿을 수 없는 진입점의 요청은 정한 대기·거절·예약 정책으로 처리한다.
- 같은 계약을 구현하는 코드가 둘 이상이면(플랫폼별, 런타임별 구현) 공유 시나리오로 같은 동작을 하는지 확인한다.

## 18. 경계 로그

문제 위치를 좁힐 수 있는 것은 경계의 입출력이 보일 때다. 경계 로그는 자리와 형식을 정하고, 사람이나 에이전트가 기억해서 쓰지 않게 한다.

- **자리.** 공개 API의 입구와 출구(런타임 경계 포함), Bridge, Coordinator의 단계, 자원 소유자의 외부 호출과 콜백. 이 지점이 Feature 내부 구현(예: Feature Data의 전용 어댑터)에 있어도 남긴다. 경계가 아닌 내부 계산과 일반 객체 호출에는 남기지 않는다. 로그를 남기려고 객체의 소유권이나 위치를 옮기지 않는다.
- **형식.** 시각, 경계 이름, 방향, 연산, 상관 식별자, 대상 식별자, 결과, 소요 시간. 상관 식별자는 요청이나 작업 실행 하나를 구분하는 값이고, 관련 경계를 따라 함께 넘긴다. 세션·기기·기록 id는 대상 식별자로 따로 둔다. 같은 실행 안의 병렬 연산과 재시도를 구분해야 하면 하위 연산 식별자와 시도 번호를 함께 남긴다.
- **작성 방식.** 계약에서 생성되는 코드나 공개 API 래퍼가 남긴다. 래퍼로 감쌀 수 없는 Bridge·Coordinator·소유자는 공용 로그 함수 하나로 남긴다.
- **고빈도 경로.** 센서 샘플이나 위치 갱신처럼 자주 지나는 값은 매번 남기지 않는다. 상태 전이와 일정 간격의 요약만 남긴다.
- **민감 정보.** 위치 좌표, 사용자 식별자, 자격 증명은 로그 함수에서 가리거나 해시한다. 호출하는 쪽에 맡기지 않는다.
- **수준.** 빌드 종류별(개발·릴리스) 수준을 정하고, 릴리스에서도 남길 경계를 정한다.
