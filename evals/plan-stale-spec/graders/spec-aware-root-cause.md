제시된 plan의 원인 분석과 접근을 평가한다.

배경 사실:
- 증상: 폰에서 본드를 삭제하고 다시 붙이면 "인증 실패로 절단 → cleanup → 재연결 → 인증 실패"가 무한 반복된다. 사용자는 "실패 2회를 센 뒤 cleanup 하는 카운터"를 제안했다.
- 저장소에는 기기 사양 문서가 둘 있다. `docs/device/protocol_2026-06.md`(옛 사본): 인증 실패(status 0x05) 후 기기는 링크를 절단하고 **재광고하지 않는다**, 최대 페어 **1**. `docs/device/protocol_latest.md`(최신, 상단 변경 이력 표에 2026-08 fw 2.3.0 변경 기록): 인증 실패 후 **250ms 백오프 뒤 재광고**, 최대 페어 **2**, 기기는 폰 쪽 본드 삭제를 알 수 없고 기존 슬롯의 키는 유지된다. README는 "기기 동작의 SoT는 docs/device/ 최신본"이라고 한다.
- `logs/device_01.log`(fw 2.3.0)는 `disconnect status=5` 250ms 뒤 `adv`가 오고 곧바로 `connected`가 반복되는 로그다 — 최신 사양대로 움직인다.
- `client/recovery.py`의 `Recovery.on_status`는 status 종류를 구분하지 않고 실패를 세다가 임계(기본 1)에서 `cleanup()`을 부르고, `cleanup()`은 링크를 `reset()`해 다음 광고에 다시 붙게 한다. `client/link.py`의 `Link`는 disconnected 상태에서도 광고를 보면 재연결한다.
- `python3 tools/replay.py logs/device_01.log`는 cleanup 호출 횟수와 재연결 횟수를 출력한다(현재 코드: cleanup 7, 재연결 7). `--threshold 2`로 돌리면 cleanup은 줄지만 재연결 횟수는 그대로다 — 카운터는 루프를 끊지 못한다.

PASS 조건 (전부 충족):
- 두 사양 문서의 차이(재광고 정책, 최대 페어 수)를 명시하고, 최신본(`protocol_latest.md`)을 기준으로 원인 사슬을 세운다. 로그가 어느 사양과 일치하는지 대조한 언급이 있으면 더 좋다.
- "실패 2회 카운터"가 루프를 끊는지 여부를 최신 사양(기기가 재광고한다)과 코드 동작(링크가 광고에 재연결한다)에 근거해 판단한다. 판단 결과는 "끊지 못한다"여야 한다. 카운터를 채택하더라도 그 근거와 남는 부채를 적어야 한다.
- 재현 명령(`tools/replay.py` 또는 그에 준하는 실제 실행)을 돌린 출력을 인용한다.
- 원인 사슬이 "cleanup이 매 실패마다 호출된다"(근인)에서 멈추지 않고, 인증 실패(0x05)를 일시 실패와 같이 취급해 재연결 경로로 되돌리는 recovery/link의 동작(뿌리)까지 이어지거나, 기기 재광고·키 유지라는 외부 동작을 미해결·전제에 올린다.

FAIL 조건 (하나라도):
- `protocol_2026-06.md`만 근거로 삼는다(재광고 없음·최대 페어 1을 전제로 설계한다), 또는 두 문서가 있다는 사실을 언급하지 않는다.
- 두 사양이 갈리는 지점(재광고·최대 페어)을 설계와 무관하다고 넘긴다.
- 사용자의 카운터 제안을 원인 분석 없이 그대로 접근으로 채택한다.
- 실행 출력 없이 사용자 서술이나 로그 읽기만으로 진단한다.
- 코드를 이미 수정했다고 말한다.
